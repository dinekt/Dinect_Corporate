## 注目技術と実践ベストプラクティス

### 生成AIの処理場所をデータ要件からルーティングする

#### 目的

生成AIの「データを保存しない」という説明と、「どの国・地域で推論処理されるか」は別の要件です。Amazon Bedrockは、指定した単一リージョンで処理するIn-Region、定められた地理的範囲内で振り分けるGeographic cross-Region、世界の対応リージョンへ振り分けるGlobal cross-Regionを区別しています。データレジデンシーが必要な業務では、モデル名だけでなく、入力の分類、送信元リージョン、推論プロファイルの送信先、監査ログを一つの設計として管理します。これにより、機密文書を意図しない地域へ送るリスクと、必要以上に利用可能なモデルや処理能力を狭める問題を両方抑えます。

#### 対象・前提

対象は、個人情報、金融情報、行政情報、顧客契約など、処理可能な国・地域が決められている生成AIワークロードです。具体例にはAmazon BedrockのGeographic cross-Region inferenceを使い、AWSアカウント、対象モデルへのアクセス権、AWS CLI、送信元リージョンでのBedrock利用権限を前提とします。AWSは2026年9月29日時点で、Claude Opus 5、Claude Sonnet 5、Claude Haiku 4.5をインドの地理的推論プロファイルから利用でき、MumbaiとHyderabadのリージョン内で処理すると案内しています。実際のモデルとリージョンの対応は変更され得るため、導入時に最新の公式一覧を確認します。

#### 手順

以下は、インド国内の顧客問い合わせを要約するシステムを想定した一般化した構成例です。顧客名、口座情報、問い合わせ原文を含む処理はインドの地理的プロファイルへ送り、個人情報を除去した公開FAQの草案だけをグローバルプロファイルで処理します。

1. 入力を「国内処理必須」「地域制約なし」「AI送信禁止」に分類し、分類不能な入力は自動送信せず人へ戻します。APIキー、認証情報、法令や契約でAI利用を禁じたデータは、どのプロファイルにも送信しません。
2. AWSのモデル一覧から対象モデルの推論プロファイルIDを取得します。名称や`in.`などの接頭辞だけで判断せず、利用するすべての送信元リージョンから`GetInferenceProfile`を実行し、応答に含まれるモデルARNのリージョンを確認します。
3. 例えばMumbaiを送信元にする場合、次のコマンドで送信先候補を取得します。`PROFILE_ID`にはコンソールまたは公式モデル一覧で確認した実値を設定します。

```bash
aws bedrock get-inference-profile \
  --region ap-south-1 \
  --inference-profile-identifier "$PROFILE_ID" \
  --query 'models[].modelArn'
```

4. IAMでは、利用する推論プロファイルと、そのプロファイルに含まれる基盤モデルだけに`bedrock:InvokeModel`を許可します。AWS OrganizationsのSCPでリージョンを制限している場合は、必要な送信先を許可するか、対象プロファイルに限定した例外を設定します。
5. アプリケーションはデータ分類からプロファイルを決定し、モデルが分類を自己判断して送信先を変えないようにします。次はルーティング判断をアプリケーション側へ固定する最小例です。

```python
import os

ROUTES = {
    "india-restricted": os.environ["INDIA_BEDROCK_PROFILE_ID"],
    "public": os.environ["GLOBAL_BEDROCK_PROFILE_ID"],
}


def select_profile(data_class: str) -> str:
    if data_class == "ai-prohibited":
        raise ValueError("This data must not be sent to a model")
    try:
        return ROUTES[data_class]
    except KeyError as exc:
        raise ValueError("Unclassified data requires human review") from exc
```

公式資料に基づく推奨は、送信元ごとに`GetInferenceProfile`の送信先を確認し、IAMとSCPで許可範囲を固定することです。上記の問い合わせ分類とPythonコードは、この仕組みを業務へ適用した一般化した構成例です。

#### 確認方法

テスト用の非機密データを各分類で送信し、国内処理必須はインド向けプロファイル、公開データはグローバルプロファイル、送信禁止と分類不能はAPI呼び出し前に停止することを確認します。クロスリージョン推論のCloudTrailイベントでは、送信元リージョンに記録された`additionalEventData.inferenceRegion`を確認し、許可した送信先だけが現れることを監視します。さらに、各送信元リージョンから取得した`GetInferenceProfile`の結果を構成証跡として保存し、変更時に差分レビューを行います。掲載したCLIとPython例は構文と分岐設計を確認していますが、AWSアカウントでのAPI呼び出しとCloudTrail確認は未実行です。

#### 注意点

地理的プロファイルは同じ地理的範囲内の複数リージョンへ入力と出力を移動できるため、単一リージョン処理が必須の契約には適しません。AWSは通常、推論先に入力と出力を保存しないと説明していますが、一部モデルでは不正利用検知の条件により保存や人手確認が生じる可能性があるため、対象モデルのデータ保持条件を個別に確認します。SCPで送信先候補の一部を拒否すると、残りのリージョンだけへ縮退せず、プロファイル全体の呼び出しが失敗する場合があります。また、データレジデンシーを満たしても、暗号化、アクセス制御、ログの個人情報、保存期間、委託先管理など他の法令・契約要件が自動的に満たされるわけではありません。
