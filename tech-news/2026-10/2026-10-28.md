## 注目技術と実践ベストプラクティス

### AI生成の研究成果を「発表」から「検証済み」へ昇格させる証拠ゲート

#### 目的

AIが生成した証明、分析、設計判断を、文章の説得力ではなく検証可能な証拠で段階管理する。今回のOpenAI発表では、自然言語原稿、Lean形式化、外部作業部会、未公開資料が成果ごとに異なり、発表の有無だけでは信頼状態を表せない。この手法は、成果物のハッシュ、機械検査、独立レビューを別々のゲートにして、「公開済み」を誤って「正しいと確認済み」と扱う問題を防ぐために選ぶ。

#### 対象・前提

対象は、AIが生成した研究原稿、規制解釈、セキュリティ分析、設計提案など、誤りの影響が大きく第三者検証が必要な成果物である。一般化した実装例はPython 3.11以上の標準ライブラリだけを使い、製品や有料プランには依存しない。実運用では、成果物を変更不能なオブジェクトストレージまたはコミットで固定し、機械検査のログとレビュー判断を成果提出者とは別の権限で記録することを前提とする。

#### 手順

まず、状態を `announced`、`artifact_fixed`、`machine_checked`、`independent_reviewed`、`verified` に分ける。公式資料に基づく考え方は、AI出力を生の研究データとして扱い、公開物と外部の理解・検証を区別することだ。次の一般化した実装例は、成果物の同一性、機械検査、2名以上の独立レビューをすべて満たすまで `verified` を返さない。

```python
from dataclasses import dataclass
from hashlib import sha256


@dataclass(frozen=True)
class Evidence:
    claim_id: str
    artifact: bytes
    expected_sha256: str
    machine_check: str
    reviewer_ids: tuple[str, ...]
    review_decision: str


def assess(evidence: Evidence) -> str:
    actual = sha256(evidence.artifact).hexdigest()
    if actual != evidence.expected_sha256:
        return "rejected: artifact_hash_mismatch"
    if evidence.machine_check != "pass":
        return "pending: machine_check"
    if evidence.review_decision != "accepted" or len(set(evidence.reviewer_ids)) < 2:
        return "pending: independent_review"
    return "verified"


artifact = b"proof-object-v1"
digest = sha256(artifact).hexdigest()
common = dict(
    claim_id="claim-042",
    artifact=artifact,
    expected_sha256=digest,
    machine_check="pass",
)

print(assess(Evidence(**common, reviewer_ids=("reviewer-a",), review_decision="pending")))
print(assess(Evidence(**common, reviewer_ids=("reviewer-a", "reviewer-b"), review_decision="accepted")))
print(assess(Evidence(**{**common, "artifact": b"changed"}, reviewer_ids=("reviewer-a", "reviewer-b"), review_decision="accepted")))
```

期待される出力は順に `pending: independent_review`、`verified`、`rejected: artifact_hash_mismatch` である。実運用では `machine_check` を文字列で自己申告させず、Lean、テスト、再計算などのCI実行結果から取り込み、レビュー判断も別のレビューシステムから参照する。ハッシュは同じ成果物を検証したことを保証するために有効だが、内容の正しさそのものは保証しない。

#### 確認方法

上記コードはPython 3.11の標準ライブラリで実行し、3つの期待出力を確認する。これは証拠ゲートの分岐を確認した結果であり、OpenAIが発表した数学・計算機科学・物理の主張を再検証したものではない。実案件では、成果物のハッシュ一致、機械検査の終了コードとログ、レビュー担当者の独立性、判断日時、対象バージョンを監査記録に残し、いずれかが欠ければ `verified` へ進めない。さらに、形式化がある場合も、形式化した命題が元の主張と一致するか、前提や公理が妥当かを専門家が確認する。

#### 注意点

形式検証は強力だが、自然言語の主張と形式化した定理のずれ、誤った前提、検証器外の実装不具合までは自動で解消しない。独立レビューを必須にすると公開速度と費用は増えるため、低リスクな下書きには段階を減らし、研究、法務、医療、セキュリティなど高影響な用途に厳格なゲートを適用する。最初のレビュー担当者を限定すると情報格差や権威の借用が生じ得るため、利益相反を開示し、可能なら成果物と検査手順を広く公開する。未公開データ、個人情報、輸出管理対象、脆弱性情報を含む場合は、公開性よりアクセス制御と責任ある開示を優先する。
