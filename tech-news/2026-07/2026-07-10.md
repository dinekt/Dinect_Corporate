### 2. TypeScript 7.0 正式安定版リリース — Go言語による書き直しで型チェック10倍高速化、VS Codeのビルド77秒→7秒

Microsoftは**TypeScript 7.0 安定版**をリリースした。最大の変更点はコンパイラ実装を**TypeScript（JavaScript）からGo言語へ全面書き直し**したことで、ネイティブコードの実行速度と共有メモリ並列処理により**最大10倍の高速化**を実現している。ベンチマークとして自社の VS Code プロジェクト（1.5百万行のTypeScript）を用いた計測では、ビルド時間が**77.8秒から7.5秒**に短縮された。技術的にはGo移植版は既存実装の型チェックロジックを構造的に忠実に移植したものであり、型チェック結果の互換性を維持しながらパース・型チェック・エミットを並列実行できるように再設計された。移行の互換性に配慮し、従来の `tsc` コマンドと並行利用できる `@typescript/typescript6` パッケージ（`tsc6` 実行ファイルを提供）も公開されている。TypeScript 7.0ではTypeScript 6.0で非推奨だった古いモジュール形式と`target`コンパイルオプションがハードエラーとなるため、既存プロジェクトは `tsconfig.json` の確認が必要だ。npm からの通常インストールで新コンパイラに切り替わる。

### TypeScript 7.0 — Go言語コンパイラ移行の実践ガイド

```bash
# TypeScript 7.0 のインストール（従来通りnpmで取得）
npm install -D typescript@7
npx tsc --version
# Version 7.0.0

# ---- 移行前チェック: tsc6 との並行利用 ----
# @typescript/typescript6 を入れると tsc6 コマンドが使える
# TypeScript 7.0 と同一プロジェクトで比較実行が可能
npm install -D @typescript/typescript6
npx tsc6 --version  # Version 6.x.x

# ---- tsconfig.json 必須更新箇所 ----
# TypeScript 6.0 で非推奨 → 7.0 でハードエラーになる設定
# 以下のような古い target / module は削除または更新が必要

# 【変更前 (NG)】
# {
#   "compilerOptions": {
#     "target": "es5",      // es5/es3 は削除済み
#     "module": "commonjs"  // 警告 → ハードエラーへ
#   }
# }

# 【変更後 (OK)】
# {
#   "compilerOptions": {
#     "target": "ES2022",
#     "module": "NodeNext",  // または "ESNext" / "Bundler"
#     "moduleResolution": "NodeNext"
#   }
# }

# ---- パフォーマンス比較 (VS Code プロジェクト: 1.5M行) ----
# tsc6 (TypeScript 6): 77.8 秒
# tsc   (TypeScript 7):  7.5 秒  ← 約10倍高速化

# ---- 並列処理の仕組み ----
# TypeScript 7.0 はパース・型チェック・エミットを並列実行
# 共有メモリ (Goroutine) による並列化で
# 大規模モノレポほど恩恵が大きい
```

TypeScript 7.0 が採用した「忠実移植（Faithful Port）」アプローチは、新コンパイラが既存の型チェック結果と完全互換であることを意味する。設計上の選択として「高速化のためにセマンティクスを変えない」方針を貫いており、移行コストが低い。ただし非推奨機能のハードエラー化は実際の移行で引っかかるケースが多く、特に古い CJS-first な設定を持つプロジェクト（Next.js 12以前相当の構成など）では `module` / `moduleResolution` の見直しが必要になる。また Rust でのTSコンパイラ実装（oxc / ezno 系）との性能比較も注目されており、Go版ネイティブコンパイラが事実上の標準になるかどうか今後の採用動向が鍵となる。

### Ill Bloom 脆弱性 — 暗号ウォレットから$500万以上が流出、不正な乱数生成器が原因

```bash
# === Ill Bloom 脆弱性 影響チェック・対応ガイド ===
# セキュリティ企業 Coinspect が公開した脆弱性（2026年7月）
# 影響: Bitcoin, Ethereum, Polygon, Rootstock, Tron, Solana ウォレット

# ---- [1] 脆弱性の概要 ----
# ウォレット作成時に「弱い疑似乱数生成器 (PRNG)」を使用していたソフトウェアが対象
# 復元フレーズ（シードフレーズ/ニーモニック）の生成に予測可能な乱数が使われると
# 攻撃者が同じシードを総当たりで再生成し資金を引き出せる

# ---- [2] 被害実績 ----
# 2026年5月27日: 協調的な攻撃で431ウォレットから約$3.1Mが一斉流出
# その後:        露出していたウォレットからUSDTで追加$2.1Mが流出
# 合計確認被害:  $5M以上（Coinspect確認済み）

# ---- [3] リスクが高いウォレットの特徴 ----
# - 2018年以前に作成されたモバイルアプリ / ブラウザ拡張ウォレット
# - 知名度の低いソフトウェアウォレット
# - ハードウェアウォレット → 影響なし（セキュアエレメントで乱数生成）
# - 主要ソフトウェアウォレット（MetaMask最新版等）→ 影響なし

# ---- [4] 自分のウォレットが安全かどうか確認する方法 ----
# 1. ウォレットの作成日を確認（古いほどリスクが高い）
# 2. ウォレットソフトウェアのバージョン・アップデート状況を確認
# 3. Coinspect の公開チェックツール: https://illbloom.org/ を参照

# ---- [5] 推奨アクション ----
echo "=== 推奨対応優先順位 ==="
echo "1. 古いソフトウェアウォレット（2018年以前）は新規ウォレットへ資産移転"
echo "2. 新しい安全なウォレットでシードを再生成（最新版をダウンロード）"
echo "3. 長期保管はハードウェアウォレット（Ledger, Trezor等）へ移行を検討"
echo "4. ブラウザ拡張ウォレットは定期的にバージョンを確認・更新"
echo "5. https://illbloom.org/ でウォレットの脆弱性情報を確認"
```

Ill Bloom が示した教訓は「暗号ウォレットの安全性は鍵管理だけでなく鍵生成のランダム性にも依存する」という点だ。特に2018〜2020年代初頭に開発された初期世代のモバイルウォレットの一部は、モバイルOS側の安全な乱数APIの知識が普及する前に実装されており、脆弱な乱数源を使っていたケースがある。今回の脆弱性は単発のCVEではなく実装パターンの問題であるため、影響を受けるウォレットソフトウェアの数は今後さらに増える可能性がある。暗号資産を保有するユーザーにとっては「ウォレットの作成時期・使用ソフトウェア・バージョン」の把握が急務だ。
