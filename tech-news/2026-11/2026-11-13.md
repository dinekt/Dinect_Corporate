## 注目技術と実践ベストプラクティス

### AIコーディングエージェントを「証拠付きパイロット」で展開する

#### 目的

証拠付きパイロットは、AIコーディングエージェントが動作したことだけでなく、誰が、どのモデルとリージョンを、どの権限で使い、停止後に本当に拒否されたかを記録して展開判断へ使う方法です。モデル品質だけでは確認できない本人性の混同、許可外経路、費用帰属の欠落、取り消せないアクセスを、小規模な非本番運用で先に検出します。AWSが公開したCodex on Bedrockの導入例は、接続確認、2利用者の分離確認、監視、停止試験を一つの合格基準として扱っており、他のエージェント基盤にも一般化できるため取り上げます。

#### 対象・前提

対象は、個人利用からチーム・組織利用へAIコーディングエージェントを広げる開発基盤、セキュリティ、FinOpsの担当者です。AWSの公開例をそのまま試す場合は、Codex、Amazon Bedrockで利用可能な対応OpenAIモデル、AWS IAM Identity Center、非本番リポジトリ、監査・メトリクス・請求データを確認できる環境が前提です。モデルとリージョンの提供状況は実行時に公式資料で確認し、パイロット用グループには推論と必要な監視先だけの権限を付与します。一般化する場合も、利用者を識別できる短期資格情報、許可モデル一覧、安全な試験タスク、証跡の保存先、停止責任者を先に決めます。

#### 手順

AWSの公開実例では、最初にIAM Identity Centerでサインインし、Bedrock Runtimeへの直接呼び出しで本人性・モデル・リージョンを切り分けて確認します。その後にCodexを許可済みモデルへ向け、非本番リポジトリで読み取り中心の安全なタスクを実行し、2人の利用者の一時セッションと監査記録が別々に残ることを確認します。最後に設定または割り当てを削除し、アクティブなセッションの扱いを決めたうえで、新しい呼び出しが拒否されることまでを合格条件にします。

次は、その確認結果を正規化した監査レコードとして受け取り、展開可否を機械判定する一般化した仮想例です。Python 3.11の標準機能だけを使い、AWSの生ログ形式を再現するものではありません。本番ではCloudTrail、Codex OpenTelemetry、請求データなどを別々に取得し、信頼できる収集処理で同じ項目へ正規化します。

```python
APPROVED_MODELS = {"openai.gpt-5.6-sol"}
APPROVED_REGIONS = {"us-east-2"}
SAFE_ACTIONS = {"read_repo"}

events = [
    {
        "phase": "pilot",
        "user": "alice@example.com",
        "principal": "arn:aws:sts::123:assumed-role/CodexPilot/alice@example.com",
        "model": "openai.gpt-5.6-sol",
        "region": "us-east-2",
        "action": "read_repo",
        "result": "allowed",
    },
    {
        "phase": "pilot",
        "user": "bob@example.com",
        "principal": "arn:aws:sts::123:assumed-role/CodexPilot/bob@example.com",
        "model": "openai.gpt-5.6-sol",
        "region": "us-east-2",
        "action": "read_repo",
        "result": "allowed",
    },
    {
        "phase": "rollback",
        "user": "alice@example.com",
        "principal": "arn:aws:sts::123:assumed-role/CodexPilot/alice@example.com",
        "result": "denied",
    },
    {
        "phase": "rollback",
        "user": "bob@example.com",
        "principal": "arn:aws:sts::123:assumed-role/CodexPilot/bob@example.com",
        "result": "denied",
    },
]

pilot = [event for event in events if event["phase"] == "pilot"]
rollback = [event for event in events if event["phase"] == "rollback"]

users = {event["user"] for event in pilot}
principals = {event["principal"] for event in pilot}
assert len(users) >= 2, "identity isolation requires at least two users"
assert len(principals) == len(users), "users share an audit principal"

assert all(event["model"] in APPROVED_MODELS for event in pilot)
assert all(event["region"] in APPROVED_REGIONS for event in pilot)
assert all(event["action"] in SAFE_ACTIONS for event in pilot)
assert all(event["result"] == "allowed" for event in pilot)

rollback_users = {event["user"] for event in rollback}
assert rollback_users == users, "rollback was not tested for every pilot user"
assert all(event["result"] == "denied" for event in rollback)

print("PASS: 2 users isolated, approved path used, rollback denied")
```

合格記録には、利用者と監査プリンシパルの対応、許可モデル・リージョン、試験タスク、監査イベント、メトリクス、請求上の根拠、停止試験の時刻と結果を残します。AWSの資料では、CodexのOpenTelemetryはクライアント活動、Bedrockの記録はサービス側利用、AWSの本人性記録とCost and Usage Reportは利用者と請求をそれぞれ説明するため、単一のログで全てを証明しない構成が推奨されています。トークン数は活動量の指標であり、実請求額の根拠には請求データを使う、という役割分担が重要です。

#### 確認方法

上記コードはPython 3.11で実行し、`PASS: 2 users isolated, approved path used, rollback denied`が表示されることを確認します。AWS、Codex、Bedrockへの実接続は未実行で、掲載データは構造を説明する仮想例です。実環境では、2人の利用者が同じ安全なタスクを行った後、監査プリンシパルが分離され、許可モデル・リージョン以外の呼び出しがなく、必要なメトリクスと監査記録が到着することを確認します。停止試験では割り当て削除後の新規セッションを使い、拒否結果を保存してから展開対象を増やします。

#### 注意点

リポジトリ内の設定ファイルや`AGENTS.md`は共有方針には使えますが、利用者が変更できる場所を企業の強制境界として扱うことはできません。ゲートウェイ経由では、クラウド側の監査記録にエンドユーザーではなくゲートウェイの実行ロールだけが残る場合があるため、利用者別の帰属はゲートウェイ自身の信頼できるログと対応付けます。OpenTelemetryへプロンプト、コード、ファイル内容、秘密情報を無制限に記録せず、必要最小限のメトリクスと承認済み属性に限定します。資格情報の割り当てを削除しても既存セッションが期限まで有効な構成があるため、緊急停止時間の要件とセッション失効手順を別途検証する必要があります。

**出典**: [AWS — OpenAI Codex on Amazon Bedrock](https://aws.amazon.com/blogs/machine-learning/openai-codex-on-amazon-bedrock/), [Guidance for Codex on AWS — Operate: Monitoring & Cost Attribution](https://github.com/openai-on-aws/guidance-codex/blob/main/docs/operate-monitoring.md)

## まとめ

- AIコーディングエージェントの導入前に、2人の利用者で本人性が分離されることと、許可モデル・リージョンだけを通ることを確認します。
- 活動量、サービス利用、本人性、実請求を別々の証拠として保存し、単一メトリクスから安全性や費用を推測しません。
- 小規模な非本番パイロットの終了時に新規呼び出しの拒否まで試し、停止可能性を確認してから展開範囲を広げます。
