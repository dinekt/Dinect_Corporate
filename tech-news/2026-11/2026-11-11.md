## 注目技術と実践ベストプラクティス

### KVキャッシュを生かすプレフィックス対応ルーティング

#### 目的

複数の推論サーバーへ長い会話やエージェント処理を分散すると、単純なラウンドロビンでは同じプロンプトの続きが別のサーバーへ送られ、既に計算したKVキャッシュを再利用できないことがあります。プレフィックス対応ルーティングは、共通の入力部分を保持するサーバーを優先し、長いシステム指示や会話履歴の再計算を減らす設計です。Google Cloudが11月10日に紹介したAIネイティブKubernetesスタックでも、llm-d 1.0の中核機能としてプレフィックスと負荷の両方を考慮するルーティングが示されており、マルチターン処理の遅延とアクセラレータ利用効率を管理する実務上の選択肢になります。

#### 対象・前提

同じシステムプロンプト、検索結果、会話履歴を繰り返し含むチャット、RAG、コーディングエージェントの自社推論基盤に適します。公式のllm-d v1.0ガイドはKubernetes上のvLLMまたはSGLangを対象とし、概算方式と、モデルサーバーが通知するKVキャッシュイベントを使う精密方式を区別しています。精密方式ではルーターとモデルサーバーのトークンID、モデル名、ブロックサイズを一致させる必要があり、追加のイベント配送とインデックス運用も伴います。以下は製品導入実績ではなく、Python 3.11以降の標準ライブラリだけで「同じモデルとテナントの候補に限定し、プレフィックス一致を優先しつつ、過負荷なら空いている候補へ逃がす」という判断を確認する一般化した構成例です。

#### 手順

ルーティングキーへ生のプロンプトを保存せず、モデル、テナント、正規化したプレフィックスからSHA-256を作ります。候補は先にモデルとテナント境界で絞り、キャッシュ一致の有無を第一順位、処理中トークン数を第二順位にして選びます。次の仮想例では`worker-a`が対象プレフィックスを保持していますが、過負荷の上限を超えた場合は`worker-b`へフォールバックします。

```python
import hashlib

def cache_key(model, tenant, prefix):
    normalized = " ".join(prefix.split())
    value = f"{model}\0{tenant}\0{normalized}".encode()
    return hashlib.sha256(value).hexdigest()

def choose(request, workers, max_inflight=4000):
    key = cache_key(request["model"], request["tenant"], request["prefix"])
    eligible = [
        worker for worker in workers
        if worker["model"] == request["model"]
        and request["tenant"] in worker["tenants"]
    ]
    if not eligible:
        raise LookupError("no authorized worker")

    unsaturated = [w for w in eligible if w["inflight_tokens"] < max_inflight]
    pool = unsaturated or eligible
    return min(
        pool,
        key=lambda w: (key not in w["cached_prefixes"], w["inflight_tokens"]),
    )

prefix = "You are a support agent. Use only the approved manual."
key = cache_key("model-x", "tenant-a", prefix)
workers = [
    {"name": "worker-a", "model": "model-x", "tenants": {"tenant-a"},
     "cached_prefixes": {key}, "inflight_tokens": 1200},
    {"name": "worker-b", "model": "model-x", "tenants": {"tenant-a"},
     "cached_prefixes": set(), "inflight_tokens": 200},
    {"name": "worker-c", "model": "model-x", "tenants": {"tenant-b"},
     "cached_prefixes": {key}, "inflight_tokens": 0},
]
request = {"model": "model-x", "tenant": "tenant-a", "prefix": prefix}

selected = choose(request, workers)
assert selected["name"] == "worker-a"

workers[0]["inflight_tokens"] = 5000
selected = choose(request, workers)
assert selected["name"] == "worker-b"
print("PASS: cache locality, load fallback, and tenant boundary verified")
```

本番のllm-dでは自作ハッシュ表ではなく、軽量な概算方式ならルーターのローカル索引、精密方式ならモデルサーバーのKVキャッシュイベントと正確なトークンIDを使います。公式ガイドは、キャッシュがある候補だけへ固着させ続けるのではなく、設定した処理能力を超えたときに負荷の低い候補へフォールバックし、その中で処理中トークン量が少ないエンドポイントを選ぶ構成を示しています。まず概算方式で効果を測り、キャッシュ退避やマルチモーダル入力など、実際のキャッシュ状態とのずれが問題になる場合に精密方式を検討すると、運用負荷とのトレードオフを段階的に評価できます。

#### 確認方法

上記コードはPython 3.11で実行確認済みで、`PASS: cache locality, load fallback, and tenant boundary verified`を得ました。これは選択ロジックの確認であり、KVキャッシュの生成、llm-d、Kubernetes、GPUやTPU上の推論は未実行です。本番では、同じ長いプレフィックスを共有して末尾だけが異なる要求を複数回送り、キャッシュ一致率、最初のトークンまでの時間、再計算された入力トークン数、エンドポイント別の待ち行列、テナント境界違反を比較します。キャッシュ対応を無効にした対照系も用意し、平均値だけでなくp95やp99の遅延と、過負荷時に別候補へ退避できることを確認します。

#### 注意点

概算方式は軽量ですが、メモリ圧迫によるキャッシュ破棄やサーバー再起動を即座に把握できず、ルーターの推定と実態がずれる可能性があります。精密方式は一致精度を高める一方、正確なトークン化、KVイベント、索引の復旧、モデルサーバーとの設定一致が必要で、公式ガイドもアクティブ・アクティブ構成の索引と負荷状態に制約を示しています。同じプレフィックスへ要求が集中すると、キャッシュ局所性を優先し過ぎてホットスポットになるため、負荷上限とフォールバックを必ず組み合わせます。ハッシュで本文を隠しても、テナント識別子、アクセスログ、頻度から機密性が損なわれる可能性があるため、ログの最小化、テナント分離、暗号化、保持期間、削除時の索引無効化を設計し、共有キャッシュを認可境界の代わりにしてはいけません。

## まとめ

- 長い共通入力を繰り返す推論基盤では、モデルとテナントで候補を絞ってから、プレフィックス一致と負荷を組み合わせてルーティングします。
- 概算方式から始め、キャッシュ状態とのずれが品質や遅延へ影響する場合だけ、KVイベントを使う精密方式を評価します。
- キャッシュ一致率だけでなく、p95・p99遅延、過負荷時の退避、テナント境界を対照系と比較します。
