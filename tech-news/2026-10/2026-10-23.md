## 注目技術と実践ベストプラクティス

### 限定された選択肢と棄却条件でAIの小さな判断を業務フローへ組み込む

#### 目的

自由文を生成させてから文字列を解釈する代わりに、候補を限定した選択と確率を受け取り、決定論的なルールで実行可否を判定する。これは、書類の振り分け、問い合わせの担当割り当て、コマンドの危険度分類など、答えの集合を事前に定義できる反復業務に向く。Decisions APIの一般提供を取り上げる理由は、モデルの推薦と業務上の権限を分離し、低信頼時に人へ戻す構成を作りやすいからである。

#### 対象・前提

対象は、正解または望ましい処理経路をラベル化でき、誤判定時の損失を評価できる業務である。OpenAIのDecisions APIはGPT‑6 Lunaを使用し、predicate、choice、scoreの3形式を提供する。公式発表時点の料金は入力100万トークン当たり0.10ドル、キャッシュ済み入力は0.01ドルで、出力トークン課金はないが、実運用前に最新の料金、利用可能地域、データ保持条件を公式資料で再確認する。法的判断、与信、医療など、人の最終判断や説明責任が必要な用途でモデル出力だけを自動執行する構成は対象外とする。

#### 手順

まず、業務側が許可する選択肢を閉じた集合として定義し、ラベルごとの判定基準と、情報不足時に選ぶ`manual_review`を用意する。次にAPIのchoice形式で候補と確率を取得し、未知の候補、低い信頼度、高リスク処理をポリシーゲートで棄却する。モデルに直接更新権限を与えず、許可済みの後段処理だけを呼び出す構成にすると、プロンプト変更やモデル更新の影響を限定できる。

実在する公開事例として、Boxは利益相反証明書30件の評価で、Decisions APIによる経路選択がResponses APIより約5倍速く、同等の精度だったとOpenAIに報告している。Boxは低信頼の判断を担当者へ回す設計も採用した。ただし、これは提供元が掲載した顧客評価であり、第三者が独立検証した一般的な性能保証ではない。

以下は、保険証明書の確認を想定した一般化した構成例である。Python 3.12の標準ライブラリだけで動き、API固有の応答を正規化した後のデータを入力とする。実プロジェクトでは、抽出、API呼び出し、ポリシーゲート、業務システム更新の順序をトランザクション要件に合わせて決める。

```python
from dataclasses import dataclass
from typing import Mapping

ALLOWED = {"auto_approve", "manual_review", "reject"}

@dataclass(frozen=True)
class Route:
    action: str
    reason: str

def policy_gate(
    choice: str,
    probabilities: Mapping[str, float],
    *,
    threshold: float = 0.85,
    high_risk: bool = False,
) -> Route:
    if choice not in ALLOWED:
        return Route("manual_review", "unknown_choice")
    confidence = probabilities.get(choice)
    if confidence is None or not 0.0 <= confidence <= 1.0:
        return Route("manual_review", "invalid_probability")
    if not confidence >= threshold:
        return Route("manual_review", "low_confidence")
    if high_risk and choice == "auto_approve":
        return Route("manual_review", "approval_requires_human")
    return Route(choice, "policy_passed")

sample = {
    "choice": "manual_review",
    "probabilities": {
        "auto_approve": 0.06,
        "manual_review": 0.89,
        "reject": 0.05,
    },
}

result = policy_gate(**sample, high_risk=True)
print({"action": result.action, "reason": result.reason})
```

入力は「補償開始日の記載が確認できない証明書」を表す正規化結果で、期待する出力は`{'action': 'manual_review', 'reason': 'policy_passed'}`である。自動承認を返した場合でも高リスクフラグが有効なら人手確認へ戻るため、モデルの推薦と実行権限は分離される。

#### 確認方法

上のPythonコードは標準Python 3.12で実行し、記載した出力になることを確認した。Decisions APIへの実リクエスト、レイテンシー、料金、Boxの評価結果はこの検証では未実行であり、公開資料の報告と区別する。導入前には、日時を固定した正解ラベル付きデータを学習・調整用と最終評価用に分け、ラベル別の誤判定、危険な自動承認、棄却率、応答時間、1件当たり費用を記録する。特に閾値の比較では、全体精度だけでなく、誤った自動処理の損失と人手確認の負荷を同時に評価する。

#### 注意点

返された確率は、業務データ上で校正済みであることを保証しないため、部署、文書種別、言語ごとに閾値を検証する必要がある。入力文書内の命令を信頼せず、機密情報の最小化、アクセス制御、監査ログ、保存期間をモデル外で管理する。選択肢を狭くすると挙動は扱いやすくなる一方、未知の事例を既存ラベルへ無理に押し込む危険があるため、棄却経路と定期的なエラー分析を残す。キャッシュは費用を抑えられるが、個別データの混入や古い基準の再利用を避け、更新日時とポリシーバージョンを記録する。

- 候補を限定できる反復判断では、自由文ではなく選択肢と確率を受け取り、低信頼・未知入力を人へ戻す。
