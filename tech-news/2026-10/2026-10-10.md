## 注目技術と実践ベストプラクティス

### モデル固有の安全評価資料をリリースゲートにする

#### 目的

生成AIの採用判断では、提供企業が安全方針を持つことと、実際に使うモデル版について必要な評価が公開・共有されていることを分けて確認します。NISTの生成AIプロファイルは、信頼性への配慮をAIの設計、開発、利用、評価へ組み込むための自主的な枠組みを示しています。モデル名、版、用途、評価資料を一つの記録に結び付け、根拠が不足する更新を自動展開せず、試験導入または人の審査へ送ることが目的です。

#### 対象・前提

外部API、オープンウェイトモデル、クラウドサービスのモデルを業務へ導入し、提供者がモデル別のシステムカード、評価結果、リリースノートを公開または契約上共有している環境が対象です。以下はPython 3で判定規則を表した一般化した構成例で、特定企業の導入実績ではありません。必要な評価項目は、利用目的、扱うデータ、外部操作の有無、業界規制に合わせて組織ごとに定義します。

#### 手順

請求書の社内要約から導入を始め、将来は支払システムの操作も検討する仮想例を使います。まず、採用候補ごとにモデル識別子、公開日、想定用途、評価資料の所在、資料の日付、審査責任者、再審査日を記録します。URL欄には確認済みの実URLだけを登録し、資料が見つからない項目は空欄にします。

```python
BASE_EVIDENCE = {"system_card", "jailbreak_eval", "privacy_eval"}
HIGH_RISK_USES = {"external_action", "sensitive_data"}

def release_decision(manifest, use_case):
    missing = sorted(
        name for name in BASE_EVIDENCE
        if not manifest["evidence"].get(name)
    )
    if missing:
        return {"status": "hold", "missing": missing}
    if (use_case in HIGH_RISK_USES and
            not manifest["evidence"].get("dangerous_capability_eval")):
        return {
            "status": "human_review",
            "missing": ["dangerous_capability_eval"],
        }
    return {"status": "pilot", "missing": []}
```

`system_card`、`jailbreak_eval`、`privacy_eval`のいずれかが欠ければ`hold`にします。社内要約のように限定された用途で基礎資料がそろえば`pilot`、外部操作や機微データを扱い、追加評価が確認できなければ`human_review`に送ります。これは一律の公式基準ではなく、公開資料の不足を承認済みと誤認しないための実装例です。

#### 確認方法

最低3ケースを用意し、基礎資料の欠落が`hold`、基礎資料がそろった社内要約が`pilot`、高リスク用途で追加資料がない場合が`human_review`になることを単体テストします。続いて、モデルの別名が同じでも提供者のスナップショットが変わった場合、資料の対象モデル名や日付が一致しない場合、再審査日を過ぎた場合に、自動展開を止められるか確認します。運用指標は、判定別の件数、審査待ち時間、証拠URLの到達性、モデル更新後に再審査された割合とし、精度や安全性の向上率を資料なしに推定しません。このコード例は記事作成時点では実システムで未実行であり、組織固有のリスク分類と承認フローを組み込んだ結合テストが必要です。

#### 注意点

公開資料があることはモデルが安全であることの証明ではなく、資料がないことも未評価の証明ではありません。公開資料はリリースより遅れる場合があるため、待機、用途を限定した試験導入、提供者への照会のいずれを選ぶかを事前に決めます。汎用的なシステムカードを別モデルや別スナップショットへ流用せず、評価対象、日付、版、利用条件を照合します。ゲートを厳しくするほど導入は遅くなるため、読み取り中心の低影響用途と、外部操作・機微データを伴う用途で要求水準を分けます。

## まとめ

- 採用するモデル名と版に対応した安全評価結果、資料の日付、対象リスクを一つの記録で確認します。
- 評価資料が欠ける更新は自動展開せず、用途に応じて待機、限定試験、人の審査へ振り分けます。
- 公開資料の有無と内部評価の有無を混同せず、高影響用途ほど追加の根拠と承認を求めます。
