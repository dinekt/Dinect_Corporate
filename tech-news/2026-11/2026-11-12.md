## 注目技術と実践ベストプラクティス

### 信頼度付き閉集合判定を人間承認ゲートへ組み込む

#### 目的

閉集合判定は、モデルに自由文を書かせる代わりに、あらかじめ定義した選択肢と確率を受け取り、業務フローの分岐へ接続する方法です。出力の解析が単純になり、問い合わせ分類、文書の適用範囲確認、エージェントのツール選択などで、判断と後続処理の境界を明示できます。今回この技術を選んだ理由は、低遅延の判定APIが利用可能になっても、信頼度をそのまま実行権限として扱わず、誤判定の損失に応じた承認ゲートを設けることが実務上の要点だからです。

#### 対象・前提

適するのは、選択肢を有限個に定義でき、誤判定時の影響と正解データを用意できる処理です。Gemini Decisions APIを利用する場合は、公式資料上、Gemini APIの`v1beta`、`google-genai` SDK 3.2以降、モデル`gemini-decision-1`が前提です。選択肢のどれにも該当しない入力に備えて`other`を設け、法務、医療、決済、セキュリティ、データ削除など高影響の処理は、確率にかかわらず人間承認へ送ります。しきい値の選定には、本番入力を代表するラベル付き検証データと、偽陽性・偽陰性のどちらを重く扱うかという業務基準が必要です。

#### 手順

一般化した構成例として、サポート問い合わせを`billing`、`technical`、`security`、`other`へ分類し、低リスクの2分類だけを自動振り分けします。次のPython 3.11コードは、APIを呼ばず、仮想の検証データと判定確率を使ってゲートだけを再現します。検証データは説明用の少数サンプルであり、実サービスの精度実績ではありません。

```python
validation = [
    {"id": "v1", "choice": "billing", "confidence": 0.96, "truth": "billing"},
    {"id": "v2", "choice": "technical", "confidence": 0.93, "truth": "technical"},
    {"id": "v3", "choice": "billing", "confidence": 0.91, "truth": "technical"},
    {"id": "v4", "choice": "security", "confidence": 0.98, "truth": "security"},
    {"id": "v5", "choice": "billing", "confidence": 0.88, "truth": "billing"},
]

AUTO_LABELS = {"billing", "technical"}
EXPECTED_LABELS = {"billing", "technical", "security", "other"}


def evaluate(threshold):
    selected = [
        item for item in validation
        if item["choice"] in AUTO_LABELS and item["confidence"] >= threshold
    ]
    error_count = sum(item["choice"] != item["truth"] for item in selected)
    error_rate = error_count / len(selected) if selected else 0.0
    return len(selected), error_rate


candidates = [0.90, 0.92, 0.95]
passing = [
    (threshold, *evaluate(threshold))
    for threshold in candidates
    if evaluate(threshold)[0] and evaluate(threshold)[1] <= 0.05
]
threshold = min(passing, key=lambda result: result[0])[0]


def route(answer):
    probabilities = answer["probabilities"]
    if set(probabilities) != EXPECTED_LABELS:
        return "reject_schema"
    if abs(sum(probabilities.values()) - 1.0) > 1e-6:
        return "reject_schema"

    choice = max(probabilities, key=probabilities.get)
    confidence = probabilities[choice]
    if choice not in AUTO_LABELS or confidence < threshold:
        return "human_review"
    return f"auto:{choice}"


assert route({"probabilities": {
    "billing": 0.94, "technical": 0.03, "security": 0.01, "other": 0.02
}}) == "auto:billing"
assert route({"probabilities": {
    "billing": 0.45, "technical": 0.42, "security": 0.03, "other": 0.10
}}) == "human_review"
assert route({"probabilities": {
    "billing": 0.01, "technical": 0.01, "security": 0.97, "other": 0.01
}}) == "human_review"

print(f"PASS: threshold={threshold:.2f}, ambiguous and high-risk cases escalated")
```

実運用では、まずシャドーモードで人間の判断とモデル出力を並行記録し、ラベル別に許容できる誤自動化率を満たすしきい値を決めます。公式資料が推奨するように、自組織の代表的な入力でしきい値を調整し、対象外判定と高影響ラベルは別のルールで承認へ送る構成が有効です。自動化率を上げるほど人手は減りますが、境界事例を誤って実行するリスクが増えるため、コストだけでなく誤判定時の損失を基準に選びます。

#### 確認方法

上記コードはPython 3.11で実行確認し、`PASS: threshold=0.92, ambiguous and high-risk cases escalated`が出力されることを確認します。Gemini Decisions APIへの実リクエストは未実行であり、コード中の確率と期待結果は仮想例です。本番導入前は、ラベル別の偽陽性・偽陰性、自動処理率、人間による差し戻し率、確率帯ごとの実正解率、遅延と費用を測定します。導入後も入力言語、媒体、製品版、問い合わせ構成の変化を監視し、分布が変わった場合はしきい値を再評価します。

#### 注意点

選択式のモデルは、適切な答えがなくても定義済みの選択肢へ確率を配分するため、`other`を追加するだけでなく、対象範囲の確認を独立したゲートにします。信頼度は最上位の答えが正しい推定確率であり、その処理を実行して安全であることや損失が小さいことを保証しません。検証データが少ない、ラベル定義が重なる、特定言語や媒体が欠ける場合、見かけ上の高信頼度でも誤判定が集中し得ます。NISTのガイダンスに沿って、代表性のあるテスト集合、人間が決める評価しきい値、継続監視、介入・停止手段を一体で設計する必要があります。

## まとめ

- 選択肢が明確な業務では、自由文生成を閉集合判定へ置き換え、出力スキーマと`other`の経路を先に固定できます。
- 自動実行のしきい値は代表的なラベル付きデータで決め、高影響ラベルと低信頼度入力は人間承認へ送ります。
- 本番投入前にシャドーモードで誤自動化率と人間の差し戻しを測り、運用後も確率の校正と入力分布を監視します。
