## 注目技術と実践ベストプラクティス

### 機密度でモデル実行先を固定するデータ境界ルーター

#### 目的

データ境界ルーターは、入力の機密度に応じて、外部API、社内クラウド、オンプレミス専門モデルのどこへ処理を送れるかをモデル実行前に決定する仕組みです。Cadenceの発表は、専門モデルの性能だけでなく、顧客管理の環境で実行できることを製品要件として扱っています。設計図、契約書、未公開コードのような情報では、モデルに「外部へ送らないで」と指示するだけでは通信を防げないため、ネットワークと認証情報を実行環境側で制御することに実務上の価値があります。

#### 対象・前提

対象は、同じ業務フローで外部の汎用モデルと社内の専門モデルを使い分ける組織です。以下はPython 3.11以降・標準ライブラリのみの一般化した構成例で、実際の推論API呼び出しは行いません。機密度は`public`、`internal`、`restricted`の3段階とし、業務システム側で確定済みのメタデータとして渡す前提です。NVIDIA OpenShell 0.1.xのような外部ランタイムを使う場合も、ルーティング判定だけでなく、ファイル、ネットワーク、資格情報の許可をエージェントのプロセス外で強制する必要があります。

#### 手順

まず、業務データの所有者が機密度を付け、AI自身に分類結果を変更させないようにします。次に、`public`だけを外部モデルへ送信可能とし、`internal`と`restricted`は社内モデルへ固定します。機密データの処理が外部ツールを要求した場合は、暗黙に許可先を広げず拒否して、人間の承認フローへ戻します。

```python
from dataclasses import dataclass
from enum import StrEnum


class Sensitivity(StrEnum):
    PUBLIC = "public"
    INTERNAL = "internal"
    RESTRICTED = "restricted"


@dataclass(frozen=True)
class Job:
    job_id: str
    sensitivity: Sensitivity
    needs_external_tools: bool = False


def route(job: Job) -> dict[str, object]:
    if job.sensitivity is not Sensitivity.PUBLIC and job.needs_external_tools:
        return {
            "job_id": job.job_id,
            "decision": "deny",
            "reason": "confidential data cannot use external tools",
        }
    if job.sensitivity is Sensitivity.PUBLIC:
        return {
            "job_id": job.job_id,
            "decision": "allow",
            "backend": "external-general",
            "network": ["api.example.ai"],
        }
    return {
        "job_id": job.job_id,
        "decision": "allow",
        "backend": "local-specialized",
        "network": [],
    }


tests = [
    Job("public-faq", Sensitivity.PUBLIC),
    Job("draft-chip", Sensitivity.RESTRICTED),
    Job("contract-search", Sensitivity.INTERNAL, needs_external_tools=True),
]

for test in tests:
    print(route(test))
```

期待する出力は、`public-faq`だけが`external-general`へ進み、`draft-chip`は通信先なしで`local-specialized`へ進み、`contract-search`は拒否されることです。この例を本番へ拡張する場合は、返された`network`を参考情報として扱うのではなく、プロキシやサンドボックスの許可リストへ変換し、モデルの出力からは変更できない位置で適用します。

#### 確認方法

上記コードのルーティング部分はPython 3.11互換環境で実行確認済みです。確認項目は、公開データだけが外部エンドポイントを持つこと、機密データの決定に外部通信先が含まれないこと、機密データと外部ツール要求の組み合わせが必ず拒否されることの3点です。本番ではさらに、外部APIへ送信したリクエストの監査ログ、拒否イベント、機密度ラベルの変更履歴を照合し、許可されていない通信がネットワーク層でも失敗することを統合テストで確認します。実際のCadence MaestroやOpenShell環境での動作確認は行っていません。

#### 注意点

最大の失敗要因は、機密度ラベルの付け間違いと、ルーターを通らない迂回経路です。オンプレミス実行でも、学習データの権利、ログ保存、管理者アクセス、依存パッケージの更新が不適切なら安全とは限りません。外部モデルを一律に禁止すると品質や処理速度が低下する可能性があり、社内モデルを維持する計算資源と運用負担も増えます。そのため、拒否率、手動承認時間、タスク品質を同時に測り、データ境界を守ったまま業務価値が得られる範囲から段階的に広げるのが適切です。

## まとめ

- 外部モデルと社内モデルを併用する場合は、入力の機密度を業務システム側で確定し、実行先と通信許可を同じポリシーで固定する。
- 小さな導入では、公開データ、機密データ、機密データ＋外部ツール要求の3ケースを作り、許可・社内処理・拒否に分岐することから試せる。
- 低価格・高速なモデルを採用するときも、能力評価に応じた権限、監視、監査を維持する。
