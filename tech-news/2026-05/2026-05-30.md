### 3. Rust for CPython が Python 3.16 をターゲットに確定 — オプション依存として PEP 化へ正式進展

Python コア開発者 **Emma Smith（emmatyping）と Kirill Podoprigora（eclips4）** が提出した「Rust for CPython」pre-PEP が Python 3.16 をターゲットバージョンに確定し、本格的な PEP 化に向けた議論が加速している。当初は Rust を必須依存とする強い提案だったが、コミュニティの反発を受けてスコープを縮小し、まず **オプション依存** として Rust 製の拡張モジュールを CPython に取り込む形に再調整された。最初の実装ターゲットは `base64` モジュールで、メモリ安全性・スレッド安全性・ゼロコスト抽象化によるパフォーマンス向上を目的としている。Guido van Rossum も基本的な方向性を支持しており、Python 3.16 がリリースされる 2027 年頃には CPython のコアに Rust コードが含まれる可能性がある。Rust が利用可能な環境では自動的に高速な Rust 実装が選ばれ、そうでない場合は既存の C 実装にフォールバックする設計が有力だ。

## 新技術・新リリース

### Rust for CPython — オプション拡張モジュールとしての統合アーキテクチャ

CPython への Rust コード統合は `PyO3` ベースのバインディングレイヤーを通じて Python ↔ Rust の境界を安全に管理する設計が有力だ。以下は `base64` モジュールを Rust で実装する場合の概念コードだ（実際の CPython 組み込みとは細部が異なる）。

```rust
// Rust 側: PyO3 を使った base64 実装イメージ
use pyo3::prelude::*;
use base64::{engine::general_purpose, Engine as _};

#[pyfunction]
fn b64encode(data: &[u8]) -> String {
    general_purpose::STANDARD.encode(data)
}

#[pyfunction]
fn b64decode(encoded: &str) -> PyResult<Vec<u8>> {
    general_purpose::STANDARD
        .decode(encoded)
        .map_err(|e| PyErr::new::<pyo3::exceptions::PyValueError, _>(e.to_string()))
}

#[pymodule]
fn _base64_rust(_py: Python<'_>, m: &PyModule) -> PyResult<()> {
    m.add_function(wrap_pyfunction!(b64encode, m)?)?;
    m.add_function(wrap_pyfunction!(b64decode, m)?)?;
    Ok(())
}
```

```python
# Python 側からは通常の base64 モジュールと同じ API で利用
import base64

data = b"Hello, Rust in CPython!"
encoded = base64.b64encode(data)
print(encoded)  # b'SGVsbG8sIFJ1c3QgaW4gQ1B5dGhvbiE='

decoded = base64.b64decode(encoded)
assert decoded == data

# ビルド時に Rust ツールチェーンが利用可能な場合は Rust 実装が自動選択される
# cargo が見つからない場合は C 実装にフォールバック（既存動作と同一）
```

CPython のビルドシステム（`Makefile` / `configure`）が `cargo` をオプションで呼び出す拡張が予定されており、Python 3.16 以降のビルドプロセスに影響する。既存の C 拡張との互換性は維持されるため、ユーザーコードの変更は不要だ。

### FortiClient EMS CVE-2026-35616 — 緊急対応チェックリスト

```bash
# --- FortiClient EMS CVE-2026-35616 (CVSS 9.1) ---
# 影響バージョン: FortiClientEMS 7.4.5 および 7.4.6 のみ（7.2 系は対象外）
# 悪用状況: CISA KEV 登録済み（2026-04-06）、継続中
# 偽装ファイル名パターン: FortiClientUpdate_*.exe, fortipatch_v*.exe

# FortiClient EMS バージョン確認（Linux）
forticlient-ems --version
# 7.4.5 hotfix 1 以降 または 7.4.7 以降で対応済み

# EKZ スティーラーの IOC ファイル確認
find /tmp /var/tmp ~/Downloads \
  -name "fortipatch_v*.exe" \
  -o -name "FortiClientUpdate_*.exe" 2>/dev/null

# 暫定緩和: EMS API ポートへの外部アクセスをホワイトリスト制限（iptables）
TRUSTED_CIDR="10.0.0.0/8"  # 管理用ネットワークに置き換える
iptables -I INPUT -p tcp --dport 8443 ! -s "$TRUSTED_CIDR" -j DROP
```

EKZ スティーラーはブラウザ保存パスワード・セッション Cookie・クレジットカード情報を収集して外部 C2 へ送信する。FortiClientEMS 7.4.5/7.4.6 環境は Fortinet のセキュリティアドバイザリ（FG-IR-26-009）を確認し、ホットフィックスを即時適用すること。

### Gitea CVE-2026-27771 — 未認証でプライベートコンテナイメージが取得可能（CVSS 8.2）

Gitea のコンテナレジストリ機能に存在する認証バイパス脆弱性 **CVE-2026-27771**（CVSS 8.2）が公開された。バージョン **1.26.2 未満** の Gitea では、認証なしのリモート攻撃者がプライベートコンテナイメージを `docker pull` で取得できる。セルフホスト型の Gitea をコンテナレジストリとして利用しているチームは、プライベートイメージに含まれる機密情報（環境変数・API キー等）の漏洩リスクがある。

```bash
# Gitea バージョン確認
gitea --version

# 1.26.2 未満の場合: Docker 環境でのアップグレード
docker pull gitea/gitea:1.26.2
docker stop gitea && docker rm gitea
# データディレクトリはマウントしたままで再起動

# 暫定緩和: コンテナレジストリ機能を無効化（app.ini）
# [packages]
# ENABLED = false
```
