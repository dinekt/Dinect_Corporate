## 注目技術と実践ベストプラクティス

### 生成UIを表示層にとどめ、実行権限をサーバー側で制御する

#### 目的

生成AIが回答の一部としてボタンやフォームを作ると、説明から操作までを連続させられます。一方で、モデルが生成した画面要素をそのまま送信、削除、購入などの権限に結び付けると、誤操作やプロンプトインジェクションが実処理へ到達します。表示を作るモデルと、操作を許可するサーバーを分離し、すべての実行要求を許可リスト、利用者権限、対象データ、確認状態で再検証することが目的です。

#### 対象・前提

ChatGPTのIntelligent UIやプラグインに限らず、LLMが操作候補や画面定義を生成し、バックエンドのツールやAPIを呼び出すアプリが対象です。例ではPython 3の関数として認可判定を示しますが、特定のSDKやプランには依存しません。実環境では、認証済み利用者の識別子、スコープ、対象レコードの所有者、操作の一意性をサーバー側で取得できることが前提です。

#### 手順

以下は請求書の確認と送信を一般化した構成例であり、公開された導入実績ではありません。

1. モデルが生成できる操作名を`preview_invoice`と`send_invoice`に限定し、任意のURL、シェルコマンド、SQLを画面から渡せない契約にします。
2. 画面のボタンは処理を直接実行せず、操作名、請求書ID、冪等性キーをサーバーへ送ります。サーバーは請求書を再取得し、利用者と所有者の一致、必要スコープ、請求書の状態を検証します。
3. 外部送信を伴う`send_invoice`は、宛先、金額、請求書番号を固定表示した確認画面を経由し、確認済みの要求だけを実行します。

```python
ALLOWED = {"preview_invoice", "send_invoice"}

def authorize(action, invoice, user, confirmed=False):
    if action not in ALLOWED:
        return "deny"
    if invoice["owner_id"] != user["id"]:
        return "deny"
    if action == "send_invoice":
        if "invoice:send" not in user["scopes"] or not confirmed:
            return "require_confirmation"
    return "allow"
```

4. 実行結果には成功・失敗だけでなく、操作名、利用者、対象ID、確認の有無、冪等性キーを記録し、同じ要求の再送で二重送信が起きないようにします。

#### 確認方法

通常の確認・送信に加え、未許可の操作名、他者所有の請求書、送信スコープの欠落、確認の取消し、同じ冪等性キーの再送をテストします。期待結果は、確認前には外部送信や書き込みが一度も行われず、不正な要求が拒否または確認待ちになり、その理由を監査ログで追跡できることです。OpenAIの公式資料は、直接指示、間接指示、書き込み操作、未対応要求を含む評価セットと、ツール引数・結果・エラー・確認状態の記録を勧めています。このコード例は記事作成時点では実システムで未実行であり、採用する認証基盤とAPIに合わせた結合テストが必要です。

#### 注意点

画面上でボタンを隠すだけでは認可にならず、APIを直接呼ばれた場合も含めてサーバーが毎回判定する必要があります。モデルへアクセストークンや秘密情報を含むデータを渡さず、必要最小限の機能と権限だけを公開します。人の確認は高影響操作の防御になりますが、確認疲れを招くため、読み取りと書き込みを分け、宛先や金額など判断に必要な差分を短く表示します。
