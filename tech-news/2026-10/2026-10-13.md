## 注目技術と実践ベストプラクティス

### 長時間AIエージェントをチェックポイントと人の承認で安全に再開する

#### 目的

長時間動くAIエージェントは、モデル呼び出し、検索、承認待ち、外部API更新の途中でプロセスが停止すると、最初からやり直したり、同じ副作用を重複実行したりする危険があります。LangGraphのチェックポイントはスレッド単位の状態を各処理境界で保存し、`interrupt()`は人の入力が届くまで実行を停止して、同じ`thread_id`から再開できます。目的は、判断が必要な操作を人へ戻しつつ、再起動後もどこまで完了したかを復元し、承認前の送信や重複処理を防ぐことです。

#### 対象・前提

対象は、メール送信、チケット更新、返金申請、コードのマージなど、数分から数日にまたがり、人の承認を挟むワークフローです。以下はPython 3.12、`langgraph>=1.2,<2`、`langgraph-checkpoint-sqlite`を前提に、請求書の督促文を人が確認して送信キューへ渡す仮想例です。SQLiteの`SqliteSaver`はローカル開発向けであり、複数プロセスを使う本番環境では公式資料が本番向けとして挙げるPostgreSQLなどの永続チェックポインターへ置き換えます。

#### 手順

次は、生成済みの督促文を表示して停止し、人が承認または修正した後だけ送信キューへ進める一般化した構成例です。実在する企業の導入事例ではなく、状態遷移を確認するための実装例です。

```python
import sqlite3
from typing import Literal, TypedDict

from langgraph.checkpoint.sqlite import SqliteSaver
from langgraph.graph import END, START, StateGraph
from langgraph.types import Command, interrupt


class State(TypedDict):
    invoice_id: str
    draft: str
    status: Literal["draft", "approved", "rejected", "queued"]
    idempotency_key: str


def review(state: State):
    decision = interrupt({
        "question": "督促文を承認しますか",
        "invoice_id": state["invoice_id"],
        "draft": state["draft"],
    })
    if decision["action"] != "approve":
        return Command(update={"status": "rejected"}, goto=END)
    return Command(
        update={
            "draft": decision.get("draft", state["draft"]),
            "status": "approved",
        },
        goto="queue_send",
    )


def queue_send(state: State):
    # 本番では、このキーに UNIQUE 制約を付けた永続 outbox へ upsert する。
    assert state["status"] == "approved"
    return {"status": "queued"}


builder = StateGraph(State)
builder.add_node("review", review)
builder.add_node("queue_send", queue_send)
builder.add_edge(START, "review")
builder.add_edge("queue_send", END)

connection = sqlite3.connect("approval.db", check_same_thread=False)
graph = builder.compile(checkpointer=SqliteSaver(connection))
config = {"configurable": {"thread_id": "invoice-2026-001"}}

pending = graph.invoke({
    "invoice_id": "2026-001",
    "draft": "お支払い状況をご確認ください。",
    "status": "draft",
    "idempotency_key": "reminder:2026-001:v1",
}, config, durability="sync")
assert pending["__interrupt__"]

result = graph.invoke(
    Command(resume={"action": "approve", "draft": "修正後の督促文"}),
    config,
    durability="sync",
)
assert result["status"] == "queued"
```

`thread_id`はワークフローの永続的な識別子として保存し、再開時にも同じ値を使います。重要操作では`durability="sync"`を選ぶと、次の処理へ進む前にチェックポイントを書き込むため、非同期書き込みより耐久性が高い一方、待ち時間は増えます。外部送信そのものはノードへ直接埋め込まず、`idempotency_key`に一意制約を付けたoutboxへ記録し、別の送信処理が一度だけ配送する構成にします。

#### 確認方法

初回実行で`status`が`draft`のまま停止し、割り込み情報に請求書IDと草案が含まれることを確認します。プロセスを終了して同じデータベースと`thread_id`で再開し、拒否なら`rejected`で終了し、承認なら修正文が保存されて`queued`へ進むことを試験します。障害試験では、承認直後とoutbox登録直後に強制終了し、再実行しても一意な`idempotency_key`の行が増えないことを確認します。掲載コードはPythonの構文検査のみ実行済みで、LangGraph依存パッケージを導入した実行、プロセス再起動、永続outbox、実際のメール送信を含む結合試験は未実行です。

#### 注意点

`interrupt()`を呼ぶノードは再開時に先頭から再実行されるため、割り込みより前の課金、送信、DB挿入は冪等でなければなりません。メモリー上のチェックポインターは再起動で失われ、SQLiteはローカル開発向けなので、本番では可用性、同時実行、バックアップ、暗号化、保持期間を満たす永続ストレージを選びます。保存状態にはプロンプト、個人情報、承認者の入力が含まれ得るため、必要最小限のデータだけを保存し、閲覧権限と削除方針を設けます。また、長期間停止した実行はコードや業務規則の更新と不整合になるため、再開前にワークフロー版、期限、対象データの最新性を検査します。

**出典**: [LangChain — LangGraph Interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts) / [LangChain — LangGraph Checkpointers](https://docs.langchain.com/oss/python/langgraph/checkpointers) / [LangChain — LangGraph Graph API](https://docs.langchain.com/oss/python/langgraph/graph-api)

## まとめ

- 新モデルは提供元の評価だけで判断せず、長時間タスク、記憶する個人情報、重要操作前の確認を自社条件で検証します。
- 人の判断を挟むエージェントは、永続チェックポイント、安定した`thread_id`、再開可能な状態遷移で設計します。
- 外部への副作用は一意な冪等キーを持つoutboxへ分離し、障害後の再実行で重複しないことを試験します。
