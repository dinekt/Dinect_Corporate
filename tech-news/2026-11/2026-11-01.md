## 注目技術と実践ベストプラクティス

### 顧客データを使わず、合成業務シナリオでAIを回帰評価する

#### 目的

合成業務シナリオ評価は、実在する顧客や従業員のデータを複製せず、業務の役割、文書、会議、期待結果を人工的に構成してAIの品質を継続測定する方法です。機密情報を評価用環境へ持ち込むリスクを減らしながら、モデル、プロンプト、検索設定の変更で既存機能が壊れていないかを再現可能に確かめられるため、企業内AIの導入前評価に適しています。Microsoft Researchの公開事例は大規模な合成企業を使いますが、ここでは同じ考え方を会議アクション抽出の小さな回帰テストへ一般化します。

#### 対象・前提

対象は、会議要約、社内検索、問い合わせ分類など、正解条件を業務担当者が定義できる生成AI機能です。実装例はPython 3.11以降の標準ライブラリだけを使い、モデルAPIへは接続せず、固定した入力・期待値・仮想出力を検証します。実運用では、合成データの作成根拠、利用許諾、生成条件、担当者レビューを記録し、用途に応じた安全性・公平性の評価項目を追加することが前提です。

#### 手順

一般化した構成例として、架空の従業員だけが参加する会議記録から、担当者、作業、期限、根拠行をJSONで抽出するAIを想定します。次のコードは、入力データが実在ドメインを含まないこと、期待値が会議記録の行を参照していること、仮想出力が期待値と一致することを検査します。`candidate` はAIを実行した結果ではなく、評価器の自己テストに使う仮想出力です。

```python
import hashlib
import json
import re

fixture = {
    "scenario_id": "meeting-actions-v1",
    "participants": [
        {"id": "SYNTH-001", "email": "aoi@example.invalid"},
        {"id": "SYNTH-002", "email": "ren@example.invalid"},
    ],
    "transcript": [
        {"line": "L1", "text": "SYNTH-001は11月5日までに在庫表を更新する。"},
        {"line": "L2", "text": "SYNTH-002は11月6日までに更新内容をレビューする。"},
    ],
    "expected": [
        {"owner": "SYNTH-001", "task": "在庫表を更新", "due": "2026-11-05", "evidence": "L1"},
        {"owner": "SYNTH-002", "task": "更新内容をレビュー", "due": "2026-11-06", "evidence": "L2"},
    ],
}

# 評価器の配線確認用。実運用ではモデルのJSON出力に置き換える。
candidate = [
    {"owner": "SYNTH-001", "task": "在庫表を更新", "due": "2026-11-05", "evidence": "L1"},
    {"owner": "SYNTH-002", "task": "更新内容をレビュー", "due": "2026-11-06", "evidence": "L2"},
]

def canonical(value):
    return json.dumps(value, ensure_ascii=False, sort_keys=True, separators=(",", ":"))

def validate_fixture(data):
    ids = {p["id"] for p in data["participants"]}
    lines = {row["line"] for row in data["transcript"]}
    assert all(re.fullmatch(r"SYNTH-\d{3}", value) for value in ids)
    assert all(p["email"].endswith("@example.invalid") for p in data["participants"])
    assert all(item["owner"] in ids and item["evidence"] in lines
               for item in data["expected"])

def exact_set_score(actual, expected):
    actual_set = {canonical(item) for item in actual}
    expected_set = {canonical(item) for item in expected}
    return len(actual_set & expected_set) / len(expected_set)

validate_fixture(fixture)
digest = hashlib.sha256(canonical(fixture).encode()).hexdigest()
score = exact_set_score(candidate, fixture["expected"])
assert score == 1.0
print("fixture_sha256=", digest)
print("schema=pass evaluator_self_test=pass")
```

この最小例を実務へ広げる際は、シナリオIDとハッシュを評価結果へ保存し、入力、期待値、プロンプト、モデル設定を同じ版として扱います。Microsoftの公開事例に基づく知見は、組織構造だけでなく文脈、行動、安全性も別々に検査することです。NIST AI RMF Playbookに基づく推奨は、テストセット、指標、評価ツール、実施条件を文書化し、想定する配備条件との差も記録することです。一般化した構成例では厳密一致を使っていますが、表現の揺れを許す業務では、項目別の正誤と根拠行の妥当性を人手評価で補う方が適します。

#### 確認方法

上記コードはPython 3.11で実行し、合成ID・予約ドメイン・根拠行の検査、固定ハッシュの生成、評価器の自己テストが通ることを確認済みです。これは評価ハーネスの配線確認であり、実際のAIモデルの精度検証は未実行です。本番候補を評価するときは、固定した合成シナリオ群に対して、必須項目の再現率、誤った担当者・期限の件数、根拠行の一致率、安全性違反を版ごとに比較し、事前に定めた合格条件を満たすか確認します。さらに、合成データだけでは見つからない失敗を把握するため、法務・プライバシー審査を経た匿名化集計や利用者報告を別系統で監視します。

#### 注意点

合成データはプライバシー上のリスクを下げますが、実データの長い尾、組織固有の曖昧さ、権限関係を完全には再現しません。公開情報や生成モデルから作る場合も、出典、ライセンス、生成条件を記録し、実在人物・企業と誤認される名称や連絡先、差別的な偏りが混入していないか確認します。正規表現による個人情報検査だけでは不十分で、機密度に応じて専用スキャナーと人手レビューを追加します。また、合成評価の点数だけを本番品質の代替にせず、配備条件に近い検証、独立したレビュー、運用後の監視を組み合わせる必要があります。

## まとめ

- 機密データを評価環境へ持ち込めない場合は、固定シード・版番号・期待値を持つ合成業務シナリオから回帰評価を始める。
- テストセット、指標、ツール、配備条件との差を記録し、合成データで再現できない失敗は限定的な本番監視と人手レビューで補う。
- 自己ホスト型モデルや会話内ファイル編集は、性能・利便性だけでなく、ライセンス、数値・引用、出力品質の確認工程まで含めて採用判断する。
