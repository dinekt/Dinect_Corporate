## 注目技術と実践ベストプラクティス

### 定型業務をモデルルーターで「軽量・標準・要承認」に分ける

#### 目的

モデルルーティングは、すべての入力を同じモデルへ送る代わりに、タスクの難しさ、機密度、業務への影響に応じて処理先を選ぶ設計です。軽い分類や短い要約には低コストのモデル、複雑な判断には標準モデル、重大な外部出力には人間承認を割り当てることで、品質を守りながら費用と待ち時間を抑えられます。Amazon BedrockのIntelligent Prompt Routingは同一モデルファミリー内で応答品質を予測して振り分ける公式機能で、Unit 42も複数モデルをタスクに応じて選ぶ独自ハーネスを公開事例として説明しています。

#### 対象・前提

複数の承認済みモデルを使い、要約、分類、下書き、顧客向け回答など性質の異なる処理を運用するチームが対象です。以下は特定クラウドのAPIを呼ばないPython 3.10以降の編集部による最小提案で、`economy`、`standard`、`approved_private`は各組織が承認済みの実モデルIDへ対応付ける論理名です。機密区分、利用可能なリージョン、保存方針、ツール権限は、ルーターを導入する前に組織の規程で固定します。

#### 手順

まずモデルへ渡す本文とは別に、信頼できる業務システム側で`kind`、`sensitivity`、`impact`、`input_chars`を付与します。次の例は、機密データを承認済みの閉域系へ寄せ、影響度が高い出力には必ず人間承認を要求し、公開情報の短い分類だけを軽量系へ送る編集部の提案です。

```python
from dataclasses import dataclass


@dataclass(frozen=True)
class Task:
    kind: str
    sensitivity: str
    impact: str
    input_chars: int


def route(task: Task) -> dict:
    if task.sensitivity in {"confidential", "personal"}:
        return {
            "route": "approved_private",
            "approval": task.impact == "high",
            "reason": "restricted_data",
        }
    if task.impact == "high":
        return {
            "route": "standard",
            "approval": True,
            "reason": "high_impact",
        }
    if task.kind in {"tagging", "short_summary"} and task.input_chars <= 8000:
        return {
            "route": "economy",
            "approval": False,
            "reason": "bounded_routine_task",
        }
    return {
        "route": "standard",
        "approval": False,
        "reason": "default_baseline",
    }


cases = [
    (Task("tagging", "public", "low", 1200), "economy", False),
    (Task("contract_summary", "confidential", "medium", 6000), "approved_private", False),
    (Task("customer_reply", "public", "high", 1800), "standard", True),
]
for task, expected_route, expected_approval in cases:
    decision = route(task)
    assert decision["route"] == expected_route
    assert decision["approval"] is expected_approval
print("router self-test: PASS")
```

実運用では、ルート名からモデルIDへの対応を設定ファイルで管理し、選択理由、モデル版、費用、待ち時間、評価結果を記録します。公式推奨としてBedrockは信頼できるフォールバックモデルを基準にし、プレイグラウンドで応答品質を評価してから本番へ進め、性能とコストを継続監視するよう案内しています。公開事例は複数モデルの使い分けが実務で採られていることを示しますが、上記の境界条件とコードはその製品実装を再現したものではありません。

#### 確認方法

上のコードはPython 3.11で実行し、3ケースが期待したルートと承認有無になり、`router self-test: PASS`が出ることを確認しました。外部モデルやAmazon Bedrockへの接続、出力品質、費用削減効果は未実行・未検証です。本番投入前は、現在の標準モデルを実際の応答先に保ったシャドーモードで推奨ルートだけを記録し、代表データセットごとの品質、費用、待ち時間、承認差し戻し率を比較してから切り替えます。

#### 注意点

入力本文中の指示から機密度や権限を決めると、プロンプトインジェクションでルートを変えられるため、分類メタデータは認証済みの業務システム側で付与し、APIゲートウェイやポリシー層でも送信先を制限します。Bedrockの公式資料では、Intelligent Prompt Routingは英語向けに最適化され、アプリ固有の性能データを判断へ反映できず、専門用途では最適にならない可能性があるため、日本語や固有業務では自社評価が不可欠です。障害時の技術的フォールバックと、低品質時に別モデルへ切り替える品質フォールバックを分け、重大な外部出力はモデル選択にかかわらず人間承認を残してください。
