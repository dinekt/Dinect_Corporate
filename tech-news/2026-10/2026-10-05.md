## 注目技術と実践ベストプラクティス

### AIエージェントを返答ではなく「終端状態」で評価する

#### 目的

業務エージェントは、正しい文章を返したり正常なツール呼び出しを行ったりしても、データベースに誤った値を残すことがあります。MicrosoftとHugging Faceが公開したThinkingBoxは、エージェントの最終回答ではなく、実行後のデータ、必要な変更、余計な副作用を実行可能な判定器で評価する仕組みです。公開ベンチマークの507件は同じ初期状態から各20回実行され、単発の成功だけでなく、繰り返して同じ結果を出せるかも測ります。この考え方は、問い合わせ管理、予約、返金、社内申請など、状態を更新するAIの受け入れ試験に適しています。

#### 対象・前提

対象は、MCPやAPIを通じてチケット、注文、予約、顧客情報などを更新するエージェントです。本番データではなく、毎回同じ初期状態へ戻せる隔離環境、期待する終端状態、変更してはいけない項目を用意します。ThinkingBox本体を再現する場合は、公式記事で検証対象とされたLinuxまたはWSL、Python 3.11以上、uv、Docker、固定したデータリリース、モデルの接続先が必要です。以下の最小例は特定製品に依存しないPython 3.12の標準機能だけを使います。

#### 手順

公開事例では、配送遅延の問い合わせを処理したエージェントが9回のツール呼び出しを正常に行いながら、配送業者の例外状態が解消していないチケットを「解決済み」にしていました。求められた状態は「保留」であり、会話の自然さやツール呼び出しの成功だけでは誤りを検出できませんでした。この例を一般化し、次の順にテストを作ります。

1. 実行前の状態と、成功時に変わる項目を宣言します。変更不要の項目を含め、許可していない副作用も失敗にします。
2. 初期状態を複製した隔離環境でエージェントを動かします。判定条件や正解データはエージェントへ渡しません。
3. 実行後にデータを独立した読み取り経路で取得し、差分を期待値と比較します。モデル自身の「完了しました」という返答は合否判定に使いません。
4. 同じ初期状態から複数回実行し、単発の成功率と、全試行に成功したタスクの割合を分けて記録します。

以下は、チケットを「保留」に変更し、返金額と担当者を変えないという要件を判定する一般化した実装例です。

```python
def verify_state(before, after, required_changes):
    keys = set(before) | set(after)
    actual_changes = {
        key: after.get(key)
        for key in keys
        if before.get(key) != after.get(key)
    }
    return actual_changes == required_changes


before = {"status": "open", "refund": 0, "owner": "support"}
required = {"status": "hold"}

assert verify_state(
    before,
    {"status": "hold", "refund": 0, "owner": "support"},
    required,
)
assert not verify_state(
    before,
    {"status": "solved", "refund": 0, "owner": "support"},
    required,
)
assert not verify_state(
    before,
    {"status": "hold", "refund": 100, "owner": "support"},
    required,
)
```

公式資料に基づく実践は、試行ごとに状態を初期化し、終端状態と副作用を決定的な判定器で確認することです。公開事例に基づく知見は、一度成功したかだけでなく、同一条件で繰り返し成功するかを別の指標として扱うことです。上記コードはその考えを単一レコードへ縮小した構成例であり、実システムではトランザクション、外部通知、重複作成なども判定対象に加えます。

#### 確認方法

掲載コードはPython 3.12で実行し、正しい終端状態だけが合格し、誤った状態と余計な返金変更が失敗することを確認済みです。実際のエージェントでは、固定したテストケースごとに初期化、実行、状態取得、判定を自動化し、少なくとも「正しい変更」「誤った値」「必要な変更の欠落」「余計な副作用」の4種類を検出できるか確認します。そのうえで同じケースを複数回実行し、全試行成功率を記録します。ThinkingBoxの公開結果はMicrosoftとHugging Face側の報告であり、この記事ではベンチマーク全体や個別モデルの数値を再実行しておらず、再現検証は未実行です。

#### 注意点

終端状態だけでは、利用者への説明、差別的な表現、必要な注意喚起など、データに残らない要件を評価できません。その場合は対象を限定した応答ルーブリックを併用し、自由形式のAI採点だけに依存しない設計が必要です。外部メールや決済のように取り消しにくい副作用は、模擬サービスへ置き換えるか、送信前の人による承認を設けます。また、テスト用の正解状態、認証情報、判定ロジックをエージェントから分離し、試行間でキャッシュやデータが混ざらないようにします。
