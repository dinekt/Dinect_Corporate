## 注目技術と実践ベストプラクティス

### AIエージェントの支払いを、目的・取引先・上限で拘束する

#### 目的

エージェントが有料API、データ、計算資源を作業中に選べると、事業者ごとの契約や前払いを減らせる一方、プロンプトインジェクションや誤計画がそのまま支出へ変わる危険があります。必要なのはウォレットを渡すことではなく、人が承認した目的、取引先、1回と累計の上限、通貨、期限を機械検証可能な委任情報へ固定することです。Mastercardの公開デモが具体化した「1回承認し、範囲内で複数回取引する」流れを題材に、決済処理の直前へ決定論的なポリシーゲートを置きます。

#### 対象・前提

対象は、AIエージェントが調査データ、画像生成、推論APIなどのデジタルサービスを少額・複数回購入する実験環境です。実際のMastercard Agent Pay for Machinesは早期アクセスとして買い手・売り手向けAPI、ツールキット、サンドボックスが案内されており、公開仕様は今後変わる可能性があります。以下の一般化した実装例はPython 3.12の標準ライブラリだけで支出可否を判定し、x402やMastercardの署名、ウォレット、精算機能を再現しません。本番利用には正式なSDK、本人・事業者確認、鍵管理、監査ログ、経理・法務の承認が別途必要です。

#### 手順

実在する公開デモでは、Hypeが「プロテインバーのキャンペーン案を作る」という仕事と予算をエージェントへ渡し、計画を確認してから資金を承認しました。エージェントはAIsaの調査とCloudflareの画像生成を選び、各サービスから`402 Payment Required`を受けるたびにバウチャーを発行し、2事業者へ計9回支払ったとMastercardは説明しています。これは発表主体によるデモであり、一般環境で同じ結果や安全性が保証された実績ではありません。

一般化した構成例では、承認時にタスクID、許可する事業者ID、通貨、累計上限、1回上限、有効期限を不変の委任情報へ保存します。エージェントが402応答を受けたら、モデルの自然言語判断ではなく次のような通常コードで、正規化済みの事業者IDと請求額を検査します。

```python
from dataclasses import dataclass


@dataclass(frozen=True)
class Mandate:
    task_id: str
    merchant_ids: frozenset[str]
    currency: str
    max_total_cents: int
    max_transaction_cents: int
    expires_at_epoch: int


def authorize(
    mandate: Mandate,
    *,
    task_id: str,
    merchant_id: str,
    currency: str,
    amount_cents: int,
    spent_cents: int,
    now_epoch: int,
) -> tuple[bool, str]:
    if task_id != mandate.task_id:
        return False, "task_mismatch"
    if merchant_id not in mandate.merchant_ids:
        return False, "merchant_not_allowed"
    if currency != mandate.currency:
        return False, "currency_mismatch"
    if now_epoch >= mandate.expires_at_epoch:
        return False, "expired"
    if amount_cents <= 0 or amount_cents > mandate.max_transaction_cents:
        return False, "transaction_limit"
    if spent_cents + amount_cents > mandate.max_total_cents:
        return False, "total_limit"
    return True, "approved"


mandate = Mandate(
    task_id="campaign-protein-bar",
    merchant_ids=frozenset({"aisa-research", "cloudflare-images"}),
    currency="USD",
    max_total_cents=6_000,
    max_transaction_cents=2_000,
    expires_at_epoch=1_800_000_000,
)

base = dict(
    mandate=mandate,
    task_id="campaign-protein-bar",
    merchant_id="aisa-research",
    currency="USD",
    amount_cents=1_200,
    spent_cents=2_400,
    now_epoch=1_799_900_000,
)

assert authorize(**base) == (True, "approved")
assert authorize(**(base | {"merchant_id": "unknown"}))[0] is False
assert authorize(**(base | {"amount_cents": 2_100}))[0] is False
assert authorize(**(base | {"spent_cents": 5_000}))[0] is False
assert authorize(**(base | {"task_id": "another-task"}))[0] is False
```

許可後に限って、公式ライブラリへ委任ID、正規化済みの請求内容、一意な取引IDを渡し、署名付きバウチャーを生成します。支出累計の予約と更新はデータベースの原子的処理にし、同じ取引IDの再送を一度だけ計上する冪等性を持たせます。サービス提供、バウチャー検証、精算結果までを同じ監査IDで結び、失敗時は新しい支払いを止めて人の確認へ送ります。

#### 確認方法

掲載コードはPython 3.12で実行し、許可された取引が`approved`になり、未許可事業者、1回上限超過、累計上限超過、別タスクへの流用が拒否されることを確認します。実際のx402通信、署名、ウォレット、MastercardのAPI、二重送信時のデータベース競合、精算は本環境では未実行です。サンドボックスでは、有効期限切れ、通貨変更、402応答の改ざん、同一取引IDの再送、承認取り消し、サービス未提供、精算不一致を故意に発生させ、残高、監査ログ、再試行結果が一致するかを確認します。本番移行の判定には、支払い成功率だけでなく、誤承認件数、拒否理由、人による解除率、二重計上、予算超過、サービス提供から精算までの遅延を用います。

#### 注意点

許可リストの事業者名や請求額をモデルの出力から直接信用すると、外部コンテンツに埋め込まれた命令で宛先や金額を差し替えられるため、信頼済みレジストリと署名済み請求情報から正規化します。複数の並行タスクが同じ予算を読むと、それぞれが上限内と判断して合計を超える競合が起きるので、支出枠を先に予約し、失敗時だけ戻します。署名バウチャーやブロックチェーン精算は認証、秘密鍵流出、返金、為替、税務、制裁・マネーロンダリング対策を自動的に解決しません。初期導入では低い上限、限定事業者、短い期限、観測可能なデジタルサービスに絞り、現物購入、送金、高額取引は毎回の人間承認へ残します。

## まとめ

- エージェントへ決済権限を渡す前に、目的、許可事業者、1回・累計上限、通貨、期限を不変の委任情報へ固定します。
- 402応答は通常コードで検証し、支出枠の原子的な予約、取引IDの冪等性、サービス提供と精算を結ぶ監査ログを用意します。
- 最初はサンドボックスと低額のデジタルサービスに限定し、高額取引や現物購入は人の都度承認へ残します。
