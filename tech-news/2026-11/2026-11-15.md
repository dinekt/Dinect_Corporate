## 注目技術と実践ベストプラクティス

### オンデバイスAIのモデル移行を出力契約で受け入れ判定する

#### 目的

オンデバイスAIの基盤モデルが更新されると、APIが同じでも、プロンプト解釈、表現、構造化結果、レイテンシーは変わり得る。Aion Instructへの移行では、Microsoftが独自プロンプト、LoRA、出力パーサー、特定の出力文字列へ依存するアプリに検証を求めており、モデル名の切り替えだけでは業務上の互換性を保証できない。そこで、入力と許容出力を機械判定できる「出力契約」として定義し、代表シナリオ、未調整の保留データ、実機性能を別々に評価する。これは設定変更や分類、定型抽出など、自由文よりも正誤条件を定めやすい機能で特に有効である。

#### 対象・前提

対象は、Windows AI APIを通じてPhi Silicaを利用し、Aion Instructへ移行するWindowsアプリである。2026年11月15日時点では、Aion Instructのスタンドアロンパッケージで検証でき、Windows Insider向け展開は11月20日、一般提供は2027年1月が予定されている。独自LoRAは再学習が必要であり、AionプレビューAPIはJSON Schemaや正規表現による制約付きデコードを直接提供していないため、構造化結果はアプリ側でも検証する。以下の一般化した構成例はPython 3.11以降の標準ライブラリだけを評価器に使うが、モデル呼び出し、Windows App SDKの版、実行順序は対象プロジェクトに合わせて組み込む。

#### 手順

まず、モデルが担う仕事を一文で固定し、入力、出力形式、許容値、正解条件、無効出力を定義する。Microsoftの公開プロンプトガイドにある仮想の設定アシスタントを一般化すると、入力は「通知とサウンドを無効にして」、出力契約は `DISABLE|["Notifications","Sounds"]`、動作は `ENABLE` または `DISABLE`、設定名は許可リスト内だけ、とできる。開発用データには通常表現、言い換え、否定、複数設定、曖昧入力、指示を含む入力を入れ、調整に使わない保留データを別にする。

次に、Phi SilicaとAion Instructへ同じ入力を送り、モデル識別子、ランタイム、ハードウェア、システムプロンプト、デコード設定、未加工出力、レイテンシーを行単位で保存する。次の最小評価器は、その結果を `results.jsonl` から読み、形式違反と正解不一致を分けて数える一般化した実装例である。JSONLの各行は `id`、`expected_action`、`expected_settings`、`output` を持つものとし、実運用では `model`、`runtime`、`hardware`、`latency_ms` も保存する。

```python
import json
import re
from pathlib import Path

ALLOWED = {"Notifications", "Sounds", "Alarm sound", "Location"}
PATTERN = re.compile(r'^(ENABLE|DISABLE)\|(\[.*\])$')

def parse_output(text):
    match = PATTERN.fullmatch(text.strip())
    if not match:
        raise ValueError("format")
    settings = json.loads(match.group(2))
    if not isinstance(settings, list) or not all(isinstance(x, str) for x in settings):
        raise ValueError("settings_type")
    if not set(settings) <= ALLOWED:
        raise ValueError("unknown_setting")
    return match.group(1), sorted(set(settings))

rows = [json.loads(line) for line in Path("results.jsonl").read_text().splitlines()]
summary = {"exact": 0, "wrong": 0, "invalid": 0}

for row in rows:
    try:
        actual = parse_output(row["output"])
        expected = (row["expected_action"], sorted(set(row["expected_settings"])))
        summary["exact" if actual == expected else "wrong"] += 1
    except (ValueError, json.JSONDecodeError):
        summary["invalid"] += 1

print(json.dumps(summary, ensure_ascii=False))
```

最後に、出力契約の合格条件と性能予算を別に設定する。たとえば「重要シナリオの形式違反は0件」「保留データで既存モデルが正解した行を新モデルが壊した件数を確認」「対象機種ごとにp50・p95レイテンシー、メモリ、GPUまたはNPU使用量を記録」とし、品質と性能のどちらが原因かを切り分ける。差分が小さい場合は複雑なプロンプトより単純なものを優先し、改善時は一度に一要素だけを変えて、保留データで過適合を確認する。

#### 確認方法

期待される結果は、各入力について `exact`、`wrong`、`invalid` のいずれかが再現可能に記録され、モデル別・シナリオタグ別に回帰箇所を追跡できることである。上記評価ロジックは合成したJSONLフィクスチャで実行し、正しい行、意味が異なる行、形式不正な行がそれぞれ別の集計へ入ることを確認する。一方、Aion Instruct本体での推論、Phi Silicaとの品質比較、Windows実機での性能測定はこの調査環境では実行していない。したがって、公開前の受け入れ判定には、対象アプリの実データを匿名化・最小化した評価セットと、利用者層を代表するNPU・GPU機種での実測が必要である。

#### 注意点

合計正解率だけでは、否定表現や重要設定だけが悪化する回帰を見落とすため、タグ別件数と「直った行・壊れた行」を併記する。保留データを見てプロンプトを調整した時点で、その行は開発用データへ移し、新しい保留データを用意する。Aion Instructでは透かし実装により独自パーサーが影響を受ける可能性があり、独自LoRAは再学習が必要なので、文字列の完全一致や既存アダプターの継続利用を前提にしない。また、GPU対応は段階的で、機種やドライバー、負荷によってレイテンシーや消費電力が変わるため、クラウドへのフォールバックを設ける場合は利用者の同意、送信データ、タイムアウト、費用を明示する。
