### 1. デジタル庁、約18万人向けAIエージェント環境と「源内基準」を公表

デジタル庁は11月6日、ガバメントAI「源内」で約18万人の政府職員を対象に、2種類のAIエージェント利用環境を提供すると発表しました。手軽にエージェントを作成・実行する「エージェントチャット」は順次導入を始め、高度なエージェントを構築する「源内工房」は2026年12月頃の導入を目指します。利用者・管理者・開発者の責務を分け、実行権限の限定、重要処理の人間承認、ログ保存、利用停止、定期評価、スキル審査などを定めた「源内基準」も公開されました。2027年2月頃には利用環境を「源内OSS Ver.2.0」として公開する予定で、行政以外の組織にもエージェント統制の具体例を示す動きです。

### 3. Google Cloud、NVIDIA Vera Rubin搭載A5Xを一般提供

Google Cloudは11月6日、NVIDIA Vera Rubin NVL72を基盤とするA5Xインスタンスを一般提供に移行したと更新しました。A5Xは基盤モデルの学習、推論、強化学習向けのベアメタル構成で、`a5x-highgpu-4g-metal`は4基のRubin GPU、1,152GBのHBM4、176 vCPU、1,440GBのメモリを備えます。大規模な推論や学習を単一の計算・ネットワーク・ストレージ基盤へ統合できる一方、利用開始にはアカウントチームへの連絡と容量予約が必要です。Compute Engineの通常SLAはA5Xに適用されないため、導入判断では性能だけでなく、容量確保、障害時の代替経路、料金とネットワーク費用を含めて評価する必要があります。

## 注目技術と実践ベストプラクティス

### 業務手順を検証可能な「実行可能スキル仕様」に変換する

#### 目的

AIエージェントへ長い自然言語の指示だけを渡すと、担当者ごとの暗黙知、例外時の停止条件、成果物の確認方法が抜けやすくなります。源内基準は、業務の目的、判断基準、参照資料、作業手順、確認方法、例外時の対応、出力形式をエージェントが実行可能な「スキル」として形式知化し、版管理・評価・共有する考え方を示しています。これを一般業務へ適用し、実行前に機械検査できる仕様へ変換することで、モデルや担当者が変わっても同じ統制条件を保ちやすくします。

#### 対象・前提

複数の公開資料を比較して下書きを作る、定型データを集計して報告する、申請内容を一次分類するといった、手順と例外を明示できる業務に適します。最終判断や外部公開を人が承認でき、利用可能なツール、データ区分、ログ保存方針を組織側で設定できることが前提です。以下は特定製品の導入事例ではなく、公開資料の改定差分を調査する一般化した実装例で、Python 3.11以降の標準ライブラリだけを使用します。

#### 手順

最初に、自然言語だけの手順書を、目的・入力・判断・例外・権限・承認・出力へ分解します。次の`skill.json`は、公開ガイドラインの旧版と新版を比較して差分レポートを下書きする仮想例です。外部公開はツール権限から除外し、出典日付が取れない場合は処理を停止するよう定義しています。

```json
{
  "id": "compare-public-guideline",
  "version": "1.0.0",
  "objective": "公開ガイドラインの旧版と新版を比較し、根拠付きの差分レポートを作る",
  "inputs": ["previous_url", "current_url"],
  "allowed_tools": ["fetch_public_document", "extract_text", "write_draft"],
  "steps": [
    {"id": "fetch", "tool": "fetch_public_document"},
    {"id": "extract", "tool": "extract_text"},
    {"id": "draft", "tool": "write_draft"}
  ],
  "decision_rules": [
    "金額、期限、対象者の変更を重要差分として扱う",
    "推測で欠落項目を補完しない"
  ],
  "references": ["previous_url", "current_url"],
  "verification": ["全差分にページ番号または節名がある", "原文と数値が一致する"],
  "exceptions": [
    {"when": "出典日付または本文を取得できない", "action": "stop_and_escalate"}
  ],
  "permissions": {"data": "public_only", "write": "draft_only"},
  "approvals": ["before_publish"],
  "output": ["summary", "changes", "sources", "unresolved_items"]
}
```

次に、実行前のCIや起動処理で仕様を検査します。以下の最小バリデーターは必須項目、ステップIDの重複、未許可ツール、停止可能な例外処理、公開前承認を確認します。

```python
import json

REQUIRED = {
    "id", "version", "objective", "inputs", "allowed_tools", "steps",
    "decision_rules", "references", "verification", "exceptions",
    "permissions", "approvals", "output"
}

with open("skill.json", encoding="utf-8") as f:
    skill = json.load(f)

errors = []
missing = sorted(REQUIRED - skill.keys())
if missing:
    errors.append(f"missing: {missing}")

step_ids = [step["id"] for step in skill.get("steps", [])]
if len(step_ids) != len(set(step_ids)):
    errors.append("duplicate step id")

allowed = set(skill.get("allowed_tools", []))
used = {step["tool"] for step in skill.get("steps", [])}
if not used <= allowed:
    errors.append(f"unapproved tools: {sorted(used - allowed)}")

exception_actions = {e.get("action") for e in skill.get("exceptions", [])}
if "stop_and_escalate" not in exception_actions:
    errors.append("fail-closed exception is missing")

if "before_publish" not in skill.get("approvals", []):
    errors.append("publish approval is missing")

if errors:
    raise SystemExit("FAIL: " + "; ".join(errors))
print(f"PASS: {skill['id']}@{skill['version']} ({len(step_ids)} steps)")
```

仕様はリポジトリで版管理し、変更時にこの検査と代表的な入力例を再実行します。判断基準や参照資料をコードへ埋め込まず仕様側に残すと、業務担当者が差分をレビューしやすい一方、自由記述が増えすぎると機械評価が難しくなるため、重要項目は列挙型や明示的なフィールドに寄せます。

#### 確認方法

上記の`skill.json`とバリデーターはPython 3.11で実行確認済みで、`PASS: compare-public-guideline@1.0.0 (3 steps)`を得ました。実際の公開資料取得、差分抽出、レポート生成は未実行です。本番導入前には、正常な改定、日付欠落、取得失敗、数値の変更、未許可ツールの追加、承認なしの公開要求をテストし、期待どおり停止または承認待ちになるかを確認します。実行後は参照資料、各ステップの結果、利用者の修正、最終承認を同じ実行IDで追跡できるようにします。

#### 注意点

仕様ファイルを整えても、実行基盤が権限境界や停止命令を強制しなければ安全性は向上しません。スキルの共有前に、利用可能なデータ区分、ツール権限、外部送信、保存期間、責任者を組織のルールと照合する必要があります。手順を細かく固定すると再現性は上がりますが、制度改定や例外への追随コストも増えるため、版番号、所有者、見直し期限を設定します。源内基準は政府環境向けの基準であり、民間組織へ適用する場合は自社の法務、情報分類、監査要件に置き換えて評価します。
