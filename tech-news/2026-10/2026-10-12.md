## 注目技術と実践ベストプラクティス

### モデル提供元の変更に備え、共通契約と評価ゲートで切り替え可能性を検証する

#### 目的

AIサービスでは、買収、モデル廃止、価格改定、障害、規約変更により、同じ提供元を使い続けられない場合があります。NIST AI RMFは、第三者のAIシステムに起因するリスクを管理し、高リスクな第三者AIの障害や事故に備えた代替手順を持つよう求めています。アプリケーションが期待する入出力を共通契約として定義し、候補モデルを本番切り替え前に同じ評価データへ通すことで、切り替え手順が文書だけでなく実行可能かを確認します。

#### 対象・前提

問い合わせ分類、文書抽出、定型要約など、出力項目と合格条件を定義できる業務が対象です。モデル呼び出し部分を提供元ごとのアダプターに分離し、プロンプト、構造化出力の定義、人が確認した評価ケースを提供元から独立して保存できることを前提とします。以下はPython 3の標準機能だけで評価ゲートを表した一般化した構成例で、特定企業の導入実績ではありません。

#### 手順

顧客問い合わせを`delivery`、`billing`、`security`へ振り分け、高リスク案件には人の確認を付ける仮想例を使います。

1. アプリケーションが受け取る共通出力を`case_id`、`route`、`needs_human`に固定し、各提供元の固有レスポンスはアダプター内でこの形へ変換します。
2. 実際の業務から個人情報を除去した代表例と、誤振り分け時の影響が大きい境界例を人が確認し、期待値として版管理します。
3. 候補モデルの出力を本番と切り離した環境で収集し、件数、型、許可値、期待値を決定的なコードで検査します。不合格なら自動切り替えせず、失敗ケースを修正または人の審査へ送ります。

```python
ROUTES = {"delivery", "billing", "security"}

CASES = {
    "late-package": {"route": "delivery", "needs_human": False},
    "duplicate-charge": {"route": "billing", "needs_human": True},
    "prompt-injection": {"route": "security", "needs_human": True},
}

def validate_output(item):
    if set(item) != {"case_id", "route", "needs_human"}:
        return "schema"
    if item["case_id"] not in CASES:
        return "unknown_case"
    if item["route"] not in ROUTES or type(item["needs_human"]) is not bool:
        return "type_or_value"
    expected = CASES[item["case_id"]]
    actual = {"route": item["route"], "needs_human": item["needs_human"]}
    return None if actual == expected else "wrong_answer"

def migration_gate(outputs):
    ids = [item.get("case_id") for item in outputs]
    if len(ids) != len(set(ids)) or set(ids) != set(CASES):
        return {"decision": "hold", "failures": ["case_coverage"]}
    failures = [
        {"case_id": item.get("case_id"), "reason": reason}
        for item in outputs
        if (reason := validate_output(item))
    ]
    return {
        "decision": "pilot" if not failures else "hold",
        "failures": failures,
    }
```

例えば、`prompt-injection`を`delivery`へ送る候補や、`needs_human`を文字列で返す候補は`hold`になります。公式資料に基づく推奨は、正解データと多様なケースを用意し、自動評価と人の評価を組み合わせ、切り替え前のゲートとして運用することです。共通契約と上記コードはその考え方を問い合わせ分類へ適用した実装例であり、実際の閾値は誤判定の損失と人が処理できる件数から決めます。

#### 確認方法

掲載コードはPython 3.12で実行し、3件すべてが期待値どおりなら`pilot`、誤った分類、型違反、ケース欠落、重複IDがあれば`hold`になることを単体テストします。実際のモデルでは、同じ入力、プロンプト版、構造化出力定義を固定して現行モデルと候補モデルを複数回実行し、ケース別の失敗、応答時間、費用、人の修正率を比較します。読み取り専用の影運用を経て、低影響な一部処理だけを候補へ流し、問題時に現行経路へ戻せることも確認します。掲載コードの単体テストは実行済みですが、実在するモデルAPIへの接続、品質比較、負荷試験、切り戻し試験は未実行です。

#### 注意点

共通契約を最小公倍数に寄せすぎると、各モデル固有の長文脈、ツール利用、動画処理などの強みを失います。共通部分と提供元固有機能を分け、固有機能を使う業務には代替不可であることと復旧方針を明記します。品質が同等でも、データ保持、処理地域、学習利用、知的財産、レート制限、料金、モデル廃止期限が異なるため、技術テストだけで切り替えを承認しません。また、評価データが本番の分布から古くなるとゲートが形骸化するため、失敗事例と業務変更を継続的に反映し、高影響な切り替えは人が最終承認します。

## まとめ

- 外部操作を行うAIには、モデル外から実行を停止し、証跡を保全できる制御面を用意します。
- AI基盤と提供元の障害・方針変更に備え、共通の入出力契約、評価データ、切り戻し手順を実際にテストします。
- 候補モデルは低影響な影運用から始め、品質だけでなくデータ条件、地域、費用、廃止期限を確認してから切り替えます。
