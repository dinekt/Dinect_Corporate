## 注目技術と実践ベストプラクティス

### 例外処理を専門エージェントと承認ゲートへ分離する

#### 目的

例外処理型のエージェントは、通常処理から外れた案件を分類し、関連する規則と業務記録を集め、解決案を作る仕組みです。単一の万能エージェントへ判断と更新権限をまとめず、例外種別ごとに役割を限定し、提案と実行の間へ承認ゲートを置くことで、説明可能性と誤更新時の影響範囲を改善できます。Worldwide Expressの公開事例では、請求書照合、価格差異、追加料金の3エージェント、運送会社別の知識ベース、人による承認、上書き履歴の監視が組み合わされています。

#### 対象・前提

対象は、請求差異、受注不備、申請差し戻しなど、例外の分類と参照すべき規則を明示できる業務です。例はPython 3.11以降の標準ライブラリだけで動作し、モデルAPIや基幹システムには接続せず、架空の請求差異に対するエージェント出力を承認待ちへ送るゲートを検証します。本番導入では、参照データへの読み取り権限、更新APIの最小権限、承認者、金額上限、監査ログの保存期間を事前に定めることが前提です。

#### 手順

一般化した構成例として、価格差異エージェントが請求額と契約額を比較し、根拠レコードを付けて異議申立てを提案します。次のコードは、例外種別、判断、根拠ID、信頼度を構造化し、根拠が入力レコードに存在する場合だけ承認キューへ登録します。`recommendation` は実在するAIの出力ではなく、承認ゲートを確認するための仮想出力です。

```python
import hashlib
import json

case = {
    "case_id": "SYNTH-INV-1001",
    "records": {
        "invoice:INV-1001": {"amount": 1250, "currency": "USD"},
        "contract:RATE-44": {"amount": 1000, "currency": "USD"},
    },
}

recommendation = {
    "agent": "pricing_variance",
    "decision": "dispute",
    "difference": 250,
    "confidence": 0.997,
    "evidence": ["invoice:INV-1001", "contract:RATE-44"],
    "explanation": "請求額が契約額を250 USD上回るため確認が必要",
}

policy = {
    "version": "approval-policy-v1",
    "allowed_agents": ["invoice_match", "pricing_variance", "accessorial_validation"],
    "auto_execute": False,
    "min_confidence": 0.99,
    "max_auto_difference": 100,
}

def canonical(value):
    return json.dumps(value, ensure_ascii=False, sort_keys=True, separators=(",", ":"))

def approval_gate(case, rec, policy):
    assert rec["agent"] in policy["allowed_agents"]
    assert rec["decision"] in {"accept", "dispute", "request_information"}
    assert 0 <= rec["confidence"] <= 1
    assert rec["evidence"] and set(rec["evidence"]) <= set(case["records"])

    needs_review = (
        not policy["auto_execute"]
        or rec["confidence"] < policy["min_confidence"]
        or abs(rec["difference"]) > policy["max_auto_difference"]
    )
    payload = {"case": case, "recommendation": rec, "policy": policy}
    return {
        "case_id": case["case_id"],
        "route": "human_review" if needs_review else "approved_for_execution",
        "policy_version": policy["version"],
        "evidence": rec["evidence"],
        "audit_sha256": hashlib.sha256(canonical(payload).encode()).hexdigest(),
    }

result = approval_gate(case, recommendation, policy)
assert result["route"] == "human_review"
print(json.dumps(result, ensure_ascii=False, indent=2))
```

公開事例に基づく知見は、例外種別ごとにエージェントの役割、入力、判断境界、出力形式を固定し、対象組織や取引先固有の規則を判断時に検索することです。一般化した構成例では自動実行を無効にし、まず読み取りと提案だけを許可します。承認履歴が十分に蓄積した後も、一律に自動化せず、例外種別と金額帯ごとの誤り率、上書き率、根拠欠落率を確認して対象範囲を段階的に広げます。小さな例外種別から始めると安全性を高めやすい一方、対象を細分化しすぎるとルーティングと知識ベースの保守コストが増えます。

#### 確認方法

上記コードはPython 3.11で実行し、仮想出力の種別、判断、信頼度、根拠IDを検査したうえで、結果が `human_review` となり、入力・提案・ポリシーから監査用SHA-256が生成されることを確認済みです。これは承認ゲートの自己テストであり、AIモデル、検索精度、基幹システム更新の検証は未実行です。本番候補では例外種別ごとに、正しい分類率、根拠レコード一致率、解決時間、人による上書き率、誤更新件数を測り、ポリシー版とモデル・プロンプト・知識ベース版を同じ監査記録へ残します。期待結果に達しない分類は提案専用のまま維持し、更新権限を付与しません。

#### 注意点

高い信頼度の数値は正しさを保証せず、モデル自身の自己申告だけで自動実行を許可してはいけません。入力文書やメールにはプロンプトインジェクションが含まれる可能性があるため、参照資料を命令として扱わず、許可済みの規則とデータだけを根拠にします。金額、権限、取引先、法的影響が大きい案件は常に人へ送るほか、更新APIには冪等キー、変更前後の記録、取消手順を用意します。公開事例の1%未満というエラー率や99%超の精度条件は同社環境の報告であり、別業務へそのまま適用する合格基準ではありません。

## まとめ

- 例外処理は種別ごとに専門化し、根拠付きの提案と実際の更新を承認ゲートで分離する。
- 最初は読み取り・提案専用で運用し、例外種別ごとの誤り率、上書き率、根拠欠落率を確認してから自動化範囲を広げる。
- 生命科学や物理装置など影響の大きいAIでは、モデル能力だけでなく、認可ユーザー、最新状態、監査ログ、停止・取消手順を設計する。
