## 注目技術と実践ベストプラクティス

### 外部チェックポイントと冪等キーで長時間エージェントを安全に再開する

#### 目的

長時間実行するエージェントは、デプロイ、タイムアウト、ネットワーク切断、ワーカー障害で途中停止する。Microsoftの長時間実行エージェント向け資料では、ランタイムが元の入力から処理を再開しても、ローカル変数や途中成果は復元されないため、アプリケーション側でチェックポイント、冪等キー、処理済み位置を永続化するよう求めている。外部チェックポイントは「どこまで完了したか」を復元し、冪等キーは再試行時の二重送信や二重更新を防ぐ。これは特定モデルに依存せず、承認待ち、複数APIの呼び出し、数時間に及ぶ調査・生成処理を安全に運用するための実務的な設計である。

#### 対象・前提

対象は、再試行可能なジョブ、外部APIへの書き込み、人間承認を含むエージェントワークフローである。以下はPython 3.11と標準ライブラリの`sqlite3`だけを使う一般化した最小実装例であり、Microsoft Foundryを実行するコードではない。本番環境では、プロセスやコンテナの外にあるトランザクション対応データベースまたは永続ストレージと、可能なら送信先サービスが受け付ける冪等キーが必要になる。Microsoft Foundryのブログは長時間実行の耐障害機能を同週に一般提供すると発表している一方、参照先の技術文書は現在もプレビューかつSLAなしと記載しているため、利用前にリージョンとサービス状態を確認する。

#### 手順

一般化した構成例として、レポート生成ジョブを`queued`、`drafted`、`approved`、`applied`の状態で管理する。最初の実行は下書き後に承認待ちで停止し、プロセスを終了する。再起動後はSQLiteから状態を読み、承認済みとして公開処理へ進むが、`job_id`から作った冪等キーを一意制約で保護するため、同じ要求をさらに再実行しても副作用は1件だけになる。

```python
from pathlib import Path
import sqlite3
import tempfile


def open_db(path: Path) -> sqlite3.Connection:
    con = sqlite3.connect(path)
    con.execute("""
        CREATE TABLE IF NOT EXISTS jobs (
            job_id TEXT PRIMARY KEY,
            state TEXT NOT NULL,
            artifact TEXT
        )
    """)
    con.execute("""
        CREATE TABLE IF NOT EXISTS effects (
            idempotency_key TEXT PRIMARY KEY,
            payload TEXT NOT NULL
        )
    """)
    con.commit()
    return con


def run(path: Path, job_id: str, approved: bool = False) -> str:
    con = open_db(path)
    try:
        with con:
            row = con.execute(
                "SELECT state, artifact FROM jobs WHERE job_id = ?",
                (job_id,),
            ).fetchone()
            if row is None:
                con.execute(
                    "INSERT INTO jobs VALUES (?, 'queued', NULL)",
                    (job_id,),
                )
                state, artifact = "queued", None
            else:
                state, artifact = row

            if state == "queued":
                artifact = "report-v1"
                con.execute(
                    "UPDATE jobs SET state = 'drafted', artifact = ? "
                    "WHERE job_id = ?",
                    (artifact, job_id),
                )
                state = "drafted"

            if state == "drafted" and not approved:
                return "waiting_approval"

            if state == "drafted":
                con.execute(
                    "UPDATE jobs SET state = 'approved' WHERE job_id = ?",
                    (job_id,),
                )
                state = "approved"

            if state == "approved":
                key = f"{job_id}:publish"
                inserted = con.execute(
                    "INSERT OR IGNORE INTO effects VALUES (?, ?)",
                    (key, artifact),
                ).rowcount
                con.execute(
                    "UPDATE jobs SET state = 'applied' WHERE job_id = ?",
                    (job_id,),
                )
                return "applied" if inserted else "already_applied"

            return "already_applied"
    finally:
        con.close()


with tempfile.TemporaryDirectory() as directory:
    db = Path(directory) / "workflow.db"
    print(run(db, "job-42"))
    print(run(db, "job-42", approved=True))
    print(run(db, "job-42", approved=True))
    con = open_db(db)
    try:
        count = con.execute("SELECT COUNT(*) FROM effects").fetchone()[0]
        print(f"side_effects={count}")
    finally:
        con.close()
```

この例の実行順序は固定で、期待する出力は`waiting_approval`、`applied`、`already_applied`、`side_effects=1`である。実際のプロジェクトでは、状態名を業務上の完了単位に合わせ、モデル呼び出しの全文ではなく、検証済み成果物の参照先、入力のハッシュ、次に実行すべき処理を保存する。外部APIが冪等キーを受け付けない場合は、送信予定を同じトランザクションで記録するトランザクショナル・アウトボックスを採用し、別ワーカーが送信済み状態を更新する方式が有効である。

#### 確認方法

上記のPythonコードはPython 3.11で実行確認し、期待どおり4行が出力され、副作用テーブルの件数が1であることを確認した。次に、`drafted`直後と外部送信直後を想定してプロセスを強制終了する障害注入テストを行い、再起動後に完了状態へ到達すること、同じ冪等キーで外部処理が増えないことを確認する。本番の評価指標には、再試行件数、重複副作用件数、承認待ち時間、完了までの再開回数、チェックポイントからの復旧時間を用いる。このコードはMicrosoft Foundryや実在する外部APIには接続しておらず、それらのサービス上での動作は未実行である。

#### 注意点

データベース更新と外部API呼び出しは別システムにまたがるため、ローカルの一意制約だけで厳密な一度限りの実行を保証できない。送信先の冪等性、アウトボックス、重複照合のいずれかを組み合わせ、障害が起きる位置ごとに再試行結果を検証する必要がある。チェックポイントには個人情報、認証情報、不要なモデル入出力を保存せず、暗号化、アクセス制御、保持期限、削除手順を定める。会話履歴や隠れたモデル状態の復元を前提にせず、検証可能な業務状態と成果物を再開の基準にすることが、モデル変更やランタイム更新にも耐える設計につながる。

## まとめ

- 長時間エージェントを試すなら、まず承認待ちや外部送信の直前に業務状態を永続化し、再起動テストを行う。
- 外部更新にはジョブ単位の冪等キーを付け、送信先が対応しない場合はトランザクショナル・アウトボックスを検討する。
- 新しい企業向けAI連携や割引契約は、機能や価格だけでなく、権限、データ区分、利用量上限、サービス提供状態と合わせて評価する。
