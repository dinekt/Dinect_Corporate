## 注目技術と実践ベストプラクティス

### 代理エージェントへ操作単位の委任証明を渡す

#### 目的

ウェブサイトがエージェント名を識別できても、そのエージェントが誰の代理で、どの操作を、どの対象に、いつまで実行してよいかは分かりません。全面許可か全面遮断だけでは、商品検索は許可しつつ購入は金額上限付きにする、といった利用者の意図を表現できません。そこで、利用者、エージェント、対象サービス、許可操作、対象資源、上限、期限、一回限りの識別子を結び付けた短命な委任証明を、操作直前にリソースサーバーで検証します。OAuth 2.0 Rich Authorization Requestsの`authorization_details`は細かな認可情報を運ぶ標準的な方法を定めており、本番設計では独自トークンではなく既存の認可基盤と標準を優先します。

#### 対象・前提

対象は、個人向けAIエージェントが利用者の代理で検索、予約、購入、文書更新などを行うAPIです。利用者の認証、エージェントのクライアント識別、HTTPS、認可サーバーとAPI側の時刻同期、操作監査が前提です。以下はPython 3.11以上の標準ライブラリだけで、委任内容の改ざん、対象サービスの取り違え、金額超過、期限切れ、再送を検査する一般化した構成例です。HMAC共有鍵をコードに置く方式は説明用であり、実運用では認可サーバーが発行する署名付きアクセストークン、鍵管理、ローテーション、失効確認へ置き換えます。

#### 手順

認可画面には「買い物を任せる」のような曖昧な文言ではなく、エージェント名、商品、操作、金額上限、期限を表示します。承認後に認可サーバーが短命な委任証明を発行し、APIはエージェントからの申告値を信用せず、署名済み内容と実際の要求を照合します。次の実装例では、5万円以下の特定商品の注文だけを許可し、上限超過と同じ証明の再利用を拒否します。

```python
import base64
import hashlib
import hmac
import json

DEMO_KEY = b"replace-with-managed-key"

def b64url(data: bytes) -> str:
    return base64.urlsafe_b64encode(data).rstrip(b"=").decode()

def unb64url(text: str) -> bytes:
    return base64.urlsafe_b64decode(text + "=" * (-len(text) % 4))

def issue(claims: dict) -> str:
    payload = json.dumps(
        claims, sort_keys=True, separators=(",", ":")
    ).encode()
    signature = hmac.new(DEMO_KEY, payload, hashlib.sha256).digest()
    return f"{b64url(payload)}.{b64url(signature)}"

def authorize(token: str, request: dict, now: int, used_nonces: set) -> dict:
    try:
        encoded_payload, encoded_signature = token.split(".", 1)
        payload = unb64url(encoded_payload)
        signature = unb64url(encoded_signature)
        expected = hmac.new(DEMO_KEY, payload, hashlib.sha256).digest()
        if not hmac.compare_digest(signature, expected):
            return {"allow": False, "reason": "bad_signature"}
        grant = json.loads(payload)
    except (ValueError, json.JSONDecodeError):
        return {"allow": False, "reason": "invalid_token"}

    checks = [
        (grant["exp"] >= now, "expired"),
        (grant["aud"] == request["aud"], "wrong_audience"),
        (request["action"] in grant["actions"], "action_not_delegated"),
        (request["resource"] in grant["resources"], "resource_not_delegated"),
        (request.get("amount_jpy", 0) <= grant["max_amount_jpy"], "amount_exceeded"),
        (grant["nonce"] not in used_nonces, "replay"),
    ]
    for passed, reason in checks:
        if not passed:
            return {"allow": False, "reason": reason}

    used_nonces.add(grant["nonce"])
    return {
        "allow": True,
        "principal": grant["principal"],
        "agent": grant["agent"],
    }

grant = {
    "principal": "user-123",
    "agent": "assistant-A",
    "aud": "shop.example",
    "actions": ["order:create"],
    "resources": ["sku:helmet-001"],
    "max_amount_jpy": 50_000,
    "exp": 2_000_000_000,
    "nonce": "delegation-demo-001",
}
token = issue(grant)
used_nonces = set()

too_high = authorize(token, {
    "aud": "shop.example", "action": "order:create",
    "resource": "sku:helmet-001", "amount_jpy": 60_000,
}, 1_900_000_000, used_nonces)
approved = authorize(token, {
    "aud": "shop.example", "action": "order:create",
    "resource": "sku:helmet-001", "amount_jpy": 49_800,
}, 1_900_000_000, used_nonces)
replayed = authorize(token, {
    "aud": "shop.example", "action": "order:create",
    "resource": "sku:helmet-001", "amount_jpy": 49_800,
}, 1_900_000_000, used_nonces)

assert too_high == {"allow": False, "reason": "amount_exceeded"}
assert approved["allow"] is True
assert replayed == {"allow": False, "reason": "replay"}
```

一般化した構成例では理解しやすさのため一つの証明を一回の注文に限定しています。実運用では、参照操作と更新操作を別の証明に分け、購入、送信、削除など不可逆な操作には短い期限、一意な要求ID、実行直前の再確認を追加します。RFC 9396の細粒度認可を利用する場合は、対象APIごとに`authorization_details`の型と項目を定義し、認可画面と監査ログが同じ意味を表示するようにします。

#### 確認方法

上のコードはPython 3.12.14で実行し、6万円の注文が`amount_exceeded`で拒否され、4万9,800円の注文だけが許可され、その証明の再利用が`replay`で拒否されることを確認しました。追加テストでは、署名改ざん、異なる`aud`、許可外の商品、期限切れ、並行した同一nonceの要求を検証対象にします。期待結果は、エージェント名が許可済みでも要求が委任範囲から外れれば拒否され、許可時には利用者とエージェントの両方が監査記録へ残ることです。実際のOAuth認可サーバー、Cloudflare製品、決済APIとの統合は未実行です。

#### 注意点

署名が正しくても、利用者が内容を理解せず承認した場合や、エージェント自体が乗っ取られた場合の安全性は保証できません。認可画面は対象、操作、金額、期限を省略せず、リスクの高い操作では別経路の確認や人間承認を設けます。nonceの再利用防止は複数サーバーで原子的に共有しなければ競合を防げず、監査ログにはトークン本体や不要な個人情報を保存しません。長期トークン、複数サービスで共通のaudience、広すぎるワイルドカード権限は漏えい時の影響を広げるため避け、拒否理由も攻撃者へ過剰な情報を与えない形で返します。
