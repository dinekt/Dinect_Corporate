## 注目技術と実践ベストプラクティス

### AIワークフローを「成功1件あたり原価」で管理する

#### 目的

エージェント型AIは、1件の依頼を終えるまでに計画、検索、ツール実行、再試行を重ねるため、チャットの回数だけでは費用を説明できません。AWSが2026年10月30日に公開したFinOps運用モデルは、費用の所有者への帰属、リクエストの可観測性、予算の強制、既定値の最適化、定期レビューを順に回し、最終的に「成功した成果1件あたりの費用」を見る設計を示しています。この指標を使うと、単価の安いモデルへ替えて失敗や再試行が増えた場合も、見かけのトークン単価ではなく業務成果まで含めて判断できます。

#### 対象・前提

対象は、問い合わせ解決、文書審査、コード修正など、ジョブ単位と成功条件を定義できる生成AI・エージェント業務です。以下の一般化した実装例はPython 3.11以降の標準ライブラリだけを使い、モデルAPIには接続せず、架空の利用記録と説明用の価格表から原価を計算します。価格表は実在サービスの料金ではないため、本番では利用するモデル、リージョン、契約、キャッシュ条件に対応する公式料金を版管理して置き換えます。各呼び出しには少なくとも `team`、`application`、`workflow`、`job_id`、モデル、入出力トークン、結果を付け、業務上の成功判定はモデル自身ではなくテストまたは担当システムから取得することが前提です。

#### 手順

一般化した構成例では、共有ゲートウェイが必須メタデータを付け、呼び出しログをジョブ単位で集約し、入力・出力の単価から費用を算出します。次に、成功ジョブ数で総費用を割って単位原価を求め、期間予算を超えた場合は新規ジョブを停止します。`events` は実在する利用記録ではなく、計算と予算ゲートを検証するための仮想入力です。

```python
from collections import defaultdict
from decimal import Decimal

prices = {
    # 説明用の仮想価格（USD / 100万トークン）
    "efficient": {"input": Decimal("1.00"), "output": Decimal("4.00")},
    "premium": {"input": Decimal("3.00"), "output": Decimal("15.00")},
}

events = [
    {
        "team": "sales-ai", "application": "renewal-copilot",
        "workflow": "risk-summary", "job_id": "SYNTH-001",
        "model": "efficient", "input_tokens": 1200,
        "output_tokens": 200, "outcome": "success",
    },
    {
        "team": "sales-ai", "application": "renewal-copilot",
        "workflow": "risk-summary", "job_id": "SYNTH-002",
        "model": "premium", "input_tokens": 2500,
        "output_tokens": 400, "outcome": "failed",
    },
]

required = {"team", "application", "workflow", "job_id", "model",
            "input_tokens", "output_tokens", "outcome"}

def event_cost(event):
    rate = prices[event["model"]]
    return (
        Decimal(event["input_tokens"]) * rate["input"]
        + Decimal(event["output_tokens"]) * rate["output"]
    ) / Decimal(1_000_000)

jobs = defaultdict(lambda: {"cost": Decimal("0"), "success": False})
for event in events:
    assert required <= event.keys()
    assert event["outcome"] in {"success", "failed"}
    jobs[event["job_id"]]["cost"] += event_cost(event)
    jobs[event["job_id"]]["success"] |= event["outcome"] == "success"

total_cost = sum((job["cost"] for job in jobs.values()), Decimal("0"))
successful_jobs = sum(job["success"] for job in jobs.values())
unit_cost = total_cost / successful_jobs if successful_jobs else None
period_budget = Decimal("0.0150")
decision = "stop_new_jobs" if total_cost >= period_budget else "allow"

assert total_cost == Decimal("0.0155")
assert successful_jobs == 1
assert unit_cost == Decimal("0.0155")
assert decision == "stop_new_jobs"
print({
    "total_usd": str(total_cost),
    "successful_jobs": successful_jobs,
    "usd_per_success": str(unit_cost),
    "decision": decision,
})
```

AWSの公式資料に基づく推奨は、最適化より先に所有者への費用帰属とリクエスト観測を整え、初期は通知だけ、費用の増加速度とリスクに応じて非同期停止または同期ゲートへ強制力を上げることです。一般化した構成例では説明を簡潔にするため期間累計だけで停止していますが、本番ではチーム、アプリ、ワークフローの各予算を持ち、業務継続に必要な例外枠と管理者の解除手順も用意します。小型モデルへの振り分けやキャッシュは費用を下げ得ますが、品質評価に合格したワークフローだけへ適用し、失敗率と再試行回数を単位原価へ反映します。

#### 確認方法

上記コードはPython 3.12で実行し、合成2ジョブの総費用が0.0155ドル、成功が1件、成功1件あたり原価が0.0155ドルとなり、0.0150ドルの期間予算を超えて `stop_new_jobs` が返ることを確認済みです。これは集計ロジックと予算ゲートの自己テストであり、実在するモデル料金、モデル品質、クラウド請求との一致は未検証です。本番候補では、請求明細とログの費用差、必須メタデータ付与率、成功率、成功1件あたり原価、再試行率、予算超過から停止までの時間を測ります。安価なモデルへ変更した後は、固定評価セットと本番の限定トラフィックで成功率が許容範囲にあることを確認し、原価だけが下がって品質が悪化する変更を採用しません。

#### 注意点

入力トークン単価だけを見ると、ツール呼び出し、再試行、キャッシュ書き込み、検索やストレージの費用が漏れ、実際の原価を過小評価します。ログへプロンプト本文や顧客データを保存すると情報漏えいにつながるため、費用分析には識別子と使用量を基本とし、本文ログは目的、アクセス権、暗号化、保持期間を別に管理します。同期ゲートは超過を即時に止められる一方、推論経路の可用性と遅延に影響し、非同期停止には超過後の猶予が生じます。AWS資料の数値やしきい値は出発点であって普遍的な基準ではないため、自社の料金、成功条件、業務影響に合わせて校正する必要があります。

## まとめ

- AIエージェントの費用は、チーム・アプリ・ワークフロー・ジョブIDを呼び出し時に付け、成功1件あたり原価で比較する。
- 予算制御は観測から始め、超過速度と業務リスクに応じて通知、非同期停止、同期ゲートを選ぶ。
- 長時間のAI利用枠や産業横断AIを採用するときも、週次上限、データ所在、人の監督、電力やクラウド費用を実行条件として確認する。
