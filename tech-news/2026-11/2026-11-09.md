## 注目技術と実践ベストプラクティス

### MCPデータゲートウェイをメタデータとポリシーで統制する

#### 目的

エージェントごとにデータベース接続、スキーマ説明、SQL生成、権限制御を実装すると、同じデータでもルールが分岐し、スキーマ変更や監査対応のたびに複数箇所を修正することになります。複数のAIクライアントが利用するデータアクセスをMCPゲートウェイへ集約し、データセットの意味をメタデータ、実行可否を機械的なポリシーとして管理することで、モデル更新とデータ統制を分離します。Amazonの公開事例では、JSONメタデータからテーブルを発見し、MCPサーバーで`SELECT`限定と監査ログを共通適用しています。

#### 対象・前提

社内分析アシスタント、運用レポート、複数の専門エージェントが同じデータレイクを参照する用途に適します。利用者認証、テーブル所有者、データ分類、許可された業務コンテキスト、監査ログの保存先が定義されていることが前提です。以下はAWS環境を再現した導入事例ではなく、Python 3.11以降の標準ライブラリでメタデータと読み取り専用ポリシーを事前検査する一般化した構成例です。

#### 手順

最初に、エージェントへ直接スキーマを埋め込まず、データ所有者がレビューできるメタデータを用意します。次の`dataset.json`は配送実績を扱う仮想例で、利用可能な業務コンテキスト、公開可能な列、制限列、更新時刻、許可操作を明示しています。`sample_values`には実データや個人情報を入れず、形式を示す合成値だけを使います。

```json
{
  "dataset_id": "delivery_metrics",
  "owner": "logistics-analytics",
  "engine": "athena",
  "database": "analytics",
  "table": "delivery_summary",
  "description": "配送実績の日次集計。個票ではなく倉庫・日単位で利用する",
  "allowed_contexts": ["daily_operations", "capacity_planning"],
  "allowed_operations": ["SELECT"],
  "columns": {
    "report_date": {"type": "date", "classification": "internal", "sample_values": ["2026-11-01"]},
    "warehouse_code": {"type": "varchar", "classification": "internal", "sample_values": ["WH-EAST-01"]},
    "delivered_count": {"type": "bigint", "classification": "internal", "sample_values": ["1200"]},
    "customer_email": {"type": "varchar", "classification": "restricted", "sample_values": []}
  },
  "freshness": {"expected_hours": 24, "last_refresh_utc": "2026-11-08T21:00:00Z"},
  "logging": {"record_query_hash": true, "record_result_rows": false}
}
```

次に、カタログ登録やCIの前に、書き込み操作、制限列のサンプル、所有者欠落、過度に古いデータを拒否します。次の最小バリデーターは説明用の固定時刻を用い、期待結果を再現できるようにしています。本番では実行基盤が取得した現在時刻と、組織のデータ分類辞書へ置き換えます。

```python
import json
from datetime import datetime, timezone

with open("dataset.json", encoding="utf-8") as f:
    dataset = json.load(f)

errors = []
required = {"dataset_id", "owner", "engine", "database", "table", "columns",
            "allowed_contexts", "allowed_operations", "freshness", "logging"}
missing = sorted(required - dataset.keys())
if missing:
    errors.append(f"missing: {missing}")

if dataset.get("allowed_operations") != ["SELECT"]:
    errors.append("only SELECT is allowed")

if not dataset.get("owner") or not dataset.get("allowed_contexts"):
    errors.append("owner and allowed_contexts are required")

for name, column in dataset.get("columns", {}).items():
    if column.get("classification") == "restricted" and column.get("sample_values"):
        errors.append(f"restricted samples: {name}")

checked_at = datetime.fromisoformat("2026-11-09T06:00:00+00:00")
refreshed_at = datetime.fromisoformat(
    dataset["freshness"]["last_refresh_utc"].replace("Z", "+00:00")
)
age_hours = (checked_at.astimezone(timezone.utc) - refreshed_at).total_seconds() / 3600
if age_hours > dataset["freshness"]["expected_hours"]:
    errors.append(f"stale data: {age_hours:.1f}h")

if dataset.get("logging", {}).get("record_result_rows"):
    errors.append("result rows must not be stored in the audit log")

if errors:
    raise SystemExit("FAIL: " + "; ".join(errors))
print(f"PASS: {dataset['dataset_id']} ({len(dataset['columns'])} columns, {age_hours:.1f}h old)")
```

この検査に合格したメタデータだけをカタログへ登録し、要求時には認証済みユーザーの業務コンテキストと`allowed_contexts`を照合します。モデルが作ったSQLは別の決定的なパーサーまたはデータ基盤のポリシーで読み取り専用かを確認し、プロンプト上の「書き込み禁止」だけに依存しません。実行後はSQL全文や結果行を無条件に保存せず、実行ID、利用者、エージェント、データセット、ポリシー版、クエリハッシュ、許可・拒否理由、件数を監査記録に残します。

#### 確認方法

上記の`dataset.json`とバリデーターはPython 3.11で実行確認済みで、`PASS: delivery_metrics (4 columns, 9.0h old)`を得ました。AWS、MCPサーバー、Athena、認証基盤との接続は未実行であり、Amazonの公開事例の15〜20秒という応答時間も再検証していません。本番候補では、許可コンテキスト、未許可コンテキスト、書き込みSQL、制限列、鮮度超過、スキーマ変更、空結果、巨大結果を含む評価セットを作り、許可・拒否結果、SQL正確性、応答時間、監査記録の欠落を測ります。

#### 注意点

共通ゲートウェイは統制を一元化できる一方、障害や設定ミスの影響範囲も大きくなるため、段階展開、冗長化、レート制限、停止手段が必要です。メタデータの説明やサンプル値はエージェントの出力へ影響するため、外部入力を無審査で登録せず、所有者レビューと版管理を行います。`SELECT`だけでも大量取得、推論による再識別、機密列との結合、コスト急増は起こり得るので、行数・スキャン量・時間範囲・列・結合先もデータ基盤側で制限します。Amazonが制限列の権限制御を今後の拡張として挙げている点からも、公開事例をそのまま完成形とみなさず、自組織の認可モデルを追加する必要があります。

## まとめ

- 複数エージェントが同じデータを使う場合は、接続コードを複製せず、MCPゲートウェイへ認証・読み取り制限・監査を集約します。
- データセットの所有者、業務コンテキスト、列分類、鮮度、許可操作をメタデータ化し、登録前に機械検査します。
- 利用指標は導入状況を示すものであり、品質や生産性は受入率、レビュー結果、完了時間など別の成果指標で確認します。
