## 注目技術と実践ベストプラクティス

### AIの対外表示・実運用・検証証拠を結ぶコントロール台帳

#### 目的

AI機能について顧客へ示す説明、実際の処理、リスクを抑える統制、評価結果を一つの台帳で対応付ける。目的は、公開文では「自動防止」と説明しているのに実装は「担当者への提案」にとどまる、といった不一致を公開前や監査前に検出することである。SECが2027年度の検査で表示の正確性と運用・統制の一致を確認すると明記したため、モデル単体の精度表だけでなく、機能ごとの説明責任を再現可能な証拠へ結ぶ価値が高い。

#### 対象・前提

対象は、AIを顧客向け機能、審査、助言、不正検知、バックオフィス、コンプライアンスなどに使い、その能力や安全性を社外へ説明する組織である。金融分野ではSEC登録主体が直接の対象となるが、以下の構成は規制業種以外でも、営業資料、製品画面、仕様書の表現を実装と照合する用途に使える。台帳には最低限、機能ID、対象範囲、意思決定方式、人の関与、責任者、適用統制、評価証拠、証拠の有効期限を含める。これは法令適合を保証する仕組みではなく、適用法令と保存要件は法務・コンプライアンス担当者が決定する。

#### 手順

最初に、Webサイト、契約資料、製品画面などにあるAI関連の対外表示を機能IDへ割り当てる。次に、同じIDへ本番の処理範囲、モデルが提案のみを行うのか自動執行するのか、人が承認する条件、停止手順を登録する。評価データと結果を改変防止された保管場所へ置き、そのハッシュ値、評価日、有効期限を台帳へ記録する。リリース審査では、表示と実装の範囲・意思決定方式が一致し、証拠が有効期限内にある場合だけ公開を許可する。

以下は一般化した構成例で、Python 3.12の標準ライブラリだけを使い、対外表示と実装の不一致、証拠ハッシュ、有効期限を確認する。1件目は不正送金の候補を人へ提示する機能として整合し、2件目は対外表示が自動遮断をうたう一方、実装は人手確認であるため差し戻す。実際の台帳では、証拠本文ではなくアクセス制御された保管先URIとハッシュを登録する。

```python
from datetime import date
from hashlib import sha256

AS_OF = date.fromisoformat("2026-10-24")

controls = [
    {
        "id": "AI-001",
        "claim": {"scope": "fraud_triage", "mode": "human_review"},
        "operation": {"scope": "fraud_triage", "mode": "human_review"},
        "owner": "fraud-ops",
        "evidence": {
            "payload": "eval-2026-10-20|cases=500|reviewed=true",
            "sha256": None,
            "expires_on": "2026-11-20",
        },
    },
    {
        "id": "AI-002",
        "claim": {"scope": "account_takeover", "mode": "auto_block"},
        "operation": {"scope": "account_takeover", "mode": "human_review"},
        "owner": "identity-team",
        "evidence": {
            "payload": "eval-2026-10-18|cases=300|reviewed=true",
            "sha256": None,
            "expires_on": "2026-11-18",
        },
    },
]

for row in controls:
    payload = row["evidence"]["payload"]
    row["evidence"]["sha256"] = sha256(payload.encode()).hexdigest()

def inspect(row):
    issues = []
    if not row.get("owner"):
        issues.append("missing_owner")
    if row["claim"]["scope"] != row["operation"]["scope"]:
        issues.append("scope_mismatch")
    if row["claim"]["mode"] != row["operation"]["mode"]:
        issues.append("mode_mismatch")
    evidence = row["evidence"]
    actual_hash = sha256(evidence["payload"].encode()).hexdigest()
    if evidence["sha256"] != actual_hash:
        issues.append("evidence_hash_mismatch")
    if date.fromisoformat(evidence["expires_on"]) < AS_OF:
        issues.append("expired_evidence")
    return issues or ["ready"]

for control in controls:
    print(control["id"], inspect(control))
```

入力は2件の台帳レコードで、期待する出力は`AI-001 ['ready']`と`AI-002 ['mode_mismatch']`である。2件目は表示を「疑わしい取引を担当者へ提示」に直すか、人の承認なしで遮断する実装とその統制・評価証拠を正式に整えない限り公開しない。

#### 確認方法

上のコードは標準Python 3.12で実行し、記載した2行の出力になることを確認した。SECの検査を受けた実在企業の環境や監査手続では未実行であり、合格を示すものではない。本番では、台帳から無作為抽出した機能について、公開表示、実行ログ、承認記録、モデル・プロンプトのバージョン、評価証拠を第三者が同じIDでたどれるか確認する。リリースごとに不一致件数、期限切れ証拠、責任者未設定、重大な誤判定を集計し、ゼロでない場合の例外承認者と期限を記録する。

#### 注意点

台帳を作るだけでは統制にならず、CIやリリース承認と接続しなければ情報が古くなる。ハッシュは改変検知には役立つが、評価設計やデータの妥当性までは保証しないため、対象集団、失敗条件、評価者も別途保存する。詳細なプロンプト、顧客データ、脆弱性情報を台帳へ直接置くと漏えい範囲が広がるので、最小限のメタデータと権限付き証拠保管を分離する。証拠を細かく残すほど保管費用と審査負荷が増えるため、影響度に応じて有効期限と検証深度を変え、低リスク機能まで同じ重さにしない。

## まとめ

- AI機能の対外表示を機能IDで本番処理、統制、評価証拠へ結び、不一致を公開前に止める。
- 証拠のハッシュと有効期限だけでなく、対象データ、失敗条件、モデル・プロンプトのバージョンを追跡する。
- 高リスク機能は第三者が表示から実行ログまで再現できるか確認し、例外には責任者と期限を付ける。
