### Codexをworkspace-writeとon-requestで最小権限運用する

**区分：OpenAI公式推奨を土台にした編集部の提案**

#### 目的

Codexが通常の編集とテストを自律的に進められる範囲を作業中のリポジトリへ限定し、外部ディレクトリやネットワークへのアクセスは承認対象にする。日常作業の操作回数を抑えながら、意図しない範囲への書き込みや外部通信を防ぐ境界を明確にする。

#### 対象・前提

ローカルのCodex CLIまたはIDE拡張で、バージョン管理されたリポジトリを扱う開発者を対象とする。公式ドキュメントでは、`workspace-write`と`on-request`の組み合わせがローカル作業向けの低リスクな自動化設定として示されている。ChatGPT Workのクラウド実行環境やWeb版ではローカルCodexと同じsandbox選択機能が公開されないため、この設定例の対象外とする。

#### 手順

一時的に試す場合は、対象リポジトリのルートで次のように起動する。

```bash
codex --sandbox workspace-write --ask-for-approval on-request
```

既定値として保存する場合は、Codexの`config.toml`へ次の内容を設定する。これはローカルCLI向けの例で、承認者をユーザーに固定し、ログインシェルとworkspace内コマンドのネットワークアクセスを無効にする。

```toml
sandbox_mode = "workspace-write"
approval_policy = "on-request"
approvals_reviewer = "user"
allow_login_shell = false

[sandbox_workspace_write]
network_access = false
```

起動後に`/permissions`で有効な権限プロファイルを確認し、`/status`でworkspaceとして扱われる範囲を確認する。複数ディレクトリへの書き込みが必要な場合はsandbox全体を解除せず、`writable_roots`やコマンド単位のrulesで必要な例外だけを追加する。

#### 確認方法

検証用リポジトリで、workspace内のテストファイル作成と既存テストの実行が承認なしで完了することを確認する。次にworkspace外への書き込みとネットワークを必要とするコマンドを試し、実行前に承認が求められるか、設定に従って拒否されることを確認する。最後に`git diff`と`git status`で変更対象が想定したリポジトリ内に限定されているかを照合する。本記事の設定例は記事作成環境のローカルCodex CLIでは未実行であり、動作確認済みとはしていない。

#### 注意点

- `approval_policy = "never"`は承認プロンプトを止める設定であり、sandboxとは別の制御である。非対話実行でも必要以上にsandboxを広げない。
- `danger-full-access`と`never`の組み合わせはファイルシステムとネットワークの境界を外すため、通常の開発作業の既定値にしない。
- 自動承認レビューを使ってもsandbox境界は変わらない。承認対象の処理を誰が審査するかが変わるだけである。
- sandboxと承認は変更内容の正しさを保証しない。テスト、CI、差分レビュー、秘密情報の管理は別に実施する。

**出典**: [OpenAI Docs — Sandbox](https://learn.chatgpt.com/docs/sandboxing) / [OpenAI Docs — Agent approvals & security](https://learn.chatgpt.com/docs/agent-approvals-security)

## まとめ

- ローカルCodexの通常作業は`workspace-write`と`on-request`を基準にし、書き込み範囲と承認境界を分ける
- 外部ディレクトリが必要な場合はsandbox解除ではなく、writable rootsやrulesで例外を限定する
- 設定後はworkspace内外の書き込み、ネットワーク、`git diff`を使って境界を実際に確認する
