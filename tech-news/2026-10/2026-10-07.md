## 注目技術と実践ベストプラクティス

### GraphRAGで変更影響を関係ごと検索する

#### 目的

通常のベクトル検索は質問に似た文書片を探すのに向きますが、複数の文書に分散したサービス、担当チーム、依存関係、障害のつながりをたどる質問では根拠を取りこぼすことがあります。GraphRAGは文書からエンティティと関係を抽出し、知識グラフ、コミュニティ階層、要約を検索コンテキストに加える手法です。ここでは、変更予定の認証基盤がどのサービスと運用チームへ影響するかを、障害記録と構成資料をまたいで確認する用途を扱います。

#### 対象・前提

対象は、設計書、障害報告、サービス台帳などに依存関係が散在し、単一文書の検索だけでは回答しにくい環境です。Microsoft GraphRAGの公式クイックスタートが示すPython 3.10〜3.12と、チャットモデル・埋め込みモデルを呼び出すAPI設定を前提とします。インデックス作成は多数のモデル呼び出しを伴うため、まず小さな非機密データセットで費用と品質を確認します。機密情報を使う場合は、利用するモデル提供者の保存・学習・処理地域の条件も事前に確認します。

#### 手順

以下は、三つの架空文書を使う一般化した構成例です。実在するシステムや障害の事例ではありません。

`input/architecture.txt`

```text
Checkout APIはPayment Serviceを呼び出す。
Payment Serviceは認証にAuth Gatewayを使う。
Auth Gatewayの担当はIdentity Teamである。
```

`input/incidents.txt`

```text
2026-09-15、Auth Gatewayの証明書更新失敗によりPayment Serviceの決済要求が失敗した。
Identity Teamが証明書をロールバックして復旧した。
```

`input/change.txt`

```text
Auth Gatewayを2026-10-20に更新する。変更責任者はIdentity Teamである。
```

1. 仮想環境を作り、`python -m pip install graphrag`でGraphRAGを導入します。`graphrag init -r ./impact-rag`を実行し、生成された`impact-rag/input`へ三つの文書を置きます。
2. `.env`と`settings.yaml`に利用するチャットモデルと埋め込みモデルを設定します。APIキーをリポジトリや文書へ書かず、秘密管理機能から環境変数として渡します。
3. まず`graphrag index -r ./impact-rag --dry-run`で構成を検査し、その後`graphrag index -r ./impact-rag`でインデックスを作成します。
4. 特定のエンティティを起点に関係をたどるため、`graphrag query -r ./impact-rag -m local "Auth Gatewayの更新で影響を受けるサービス、根拠となる依存関係、担当チームを示して"`を実行します。データ全体の傾向を要約する`global`検索より、今回のような固有サービスの影響分析には`local`検索が適します。
5. 回答だけを採用せず、生成されたエンティティ、関係、参照テキストを確認し、`Checkout API → Payment Service → Auth Gateway`と担当チーム、過去障害の根拠がそろっているかをレビューします。

公式資料に基づく推奨は、小規模なチュートリアルデータから始め、クエリの性質に応じて`local`と`global`を使い分けることです。上記の変更影響データと合格条件は、関係検索を評価するための一般化した構成例です。

#### 確認方法

期待結果を先に「影響対象にPayment ServiceとCheckout APIを含む」「担当としてIdentity Teamを示す」「各判断を入力文書へ戻せる」の3条件で固定します。同じ質問を通常のベクトル検索とGraphRAGで各5回実行し、条件充足数、根拠の誤り、応答時間、索引作成と検索の費用を比較します。さらに、依存関係を一つ削除した対照データで、存在しない接続を推測しないことを確認します。掲載したコマンドは公式CLI仕様と照合していますが、モデルAPIを使ったインデックス作成と検索は未実行です。

#### 注意点

GraphRAGは、関係をまたぐ質問やデータ全体の把握に向く一方、単純な文書検索では索引作成の費用と運用複雑性が利点を上回る場合があります。グラフはモデルが抽出するため、誤ったエンティティ統合、欠落した関係、古い台帳を正しい構造として扱う危険があります。アクセス権の異なる文書を一つのグラフへ混ぜると、検索結果やコミュニティ要約から権限外の関係が漏れる可能性があるため、権限境界ごとに索引を分けるか、取得時の認可を別途実装します。索引の更新頻度、削除反映、根拠へのリンク、評価用の正解セットを運用に含め、グラフの見栄えだけで採用を決めないことが重要です。
