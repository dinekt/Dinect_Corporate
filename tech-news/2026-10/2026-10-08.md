## 注目技術と実践ベストプラクティス

### 小型モデルを一次処理に使い、難しい案件だけ上位モデルへ送る

#### 目的

大量の定型処理を低価格・低遅延の小型モデルへ任せ、判断が難しい案件やリスクの高い案件だけを上位モデルまたは人へ送る構成です。モデルごとの単価だけでなく、正しく完了した1件当たりの費用、待ち時間、見逃し率を合わせて評価できる点に実務上の価値があります。Anthropicの公式資料も、高頻度で単純な処理には効率優先で始め、実データの評価で能力不足が確認された部分だけ上位モデルへ移す方法を示しています。

#### 対象・前提

問い合わせ分類、文書要約、項目抽出など、正解例を用意でき、誤りを自動検査または人手確認へ回せる業務が対象です。Claude Haiku 5.5を使う場合、10万トークンを境に単価が変わるため、通常の入力長とキャッシュ利用を含めて費用を見積もります。構造化出力を使う場合は、採用するモデルと接続先がJSON Schemaに対応していることを、導入時点のModels APIまたは公式対応表で確認します。

#### 手順

以下は問い合わせ一次分類を一般化した構成例であり、公開された導入実績ではありません。

1. 過去の問い合わせから、通常例、曖昧例、セキュリティ・法務に関わる例を含む評価セットを作り、期待する分類と要確認フラグを人が付けます。
2. 小型モデルには`category`、`summary`、`needs_review`だけを返すJSON Schemaを指定します。`category`は`general`、`billing`、`security`、`legal`の列挙型にし、自由記述による表記揺れを防ぎます。
3. アプリ側ではモデルの自己申告だけに頼らず、APIエラー、`security`または`legal`、`needs_review=true`を上位モデルまたは人の確認へ送ります。

```python
ALWAYS_ESCALATE = {"security", "legal"}

def next_step(result: dict, api_error: bool = False) -> str:
    if api_error:
        return "human_review"
    if result["category"] in ALWAYS_ESCALATE:
        return "frontier_model_or_human"
    if result["needs_review"]:
        return "frontier_model_or_human"
    return "accept"
```

4. 評価セットで小型モデル単独、上位モデル単独、振り分け構成を同じ入力で比較し、合格基準を満たした構成だけを段階的に本番へ出します。

#### 確認方法

評価セットに対する分類のMacro F1、セキュリティ・法務案件の再現率、確認へ回した比率、正しく完了した1件当たりの費用、応答時間を記録します。特に高リスク案件の見逃しを通常分類の平均精度と分けて確認し、誤分類が許容値を超える場合は振り分け規則またはモデルを見直します。この構成例とコードは記事作成時点では実APIで未実行であり、動作確認済みの結果や改善率を示すものではありません。

#### 注意点

構造化出力が保証するのはスキーマへの適合であり、分類内容の正しさではありません。モデルが返す`needs_review`だけでは見逃しを防げないため、機密性や法的影響など業務ルールで強制的に確認へ回す条件を併用します。また、入力データの保存方針、リージョン、ログのマスキング、モデル更新時の再評価を事前に決め、単価変更や長文料金も継続的に監視します。
